# Hands-On Practice with Everyday Network Commands

The command dictionary answers "which options does this command take," the methodology page answers "in what order should I think," and this page handles the third thing: **type it out once, and wire commands, readings, and conclusions into muscle memory**. Every scenario is a closed loop you can walk in three minutes -- state the goal, run a command sequence with realistic output, read each line to say "what does this line prove," then point at where to go next. The eight tracks run from local configuration all the way to packet capture and measured bandwidth, covering nine out of ten moves in everyday troubleshooting; the full per-command option lists are out of scope here -- see [Network Management Commands](../commands/network/network.md) and [Network Tools](../commands/network/network-tools.md) -- and for the layered reasoning methodology see [Network Troubleshooting](./troubleshooting.md).

> Content adapted from the man pages and Bird's Private Recipes (conceptual framework); see the references at the end.

## How to Use This Page

Every scenario is organized as "goal -> command -> reading -> next step," and it is worth spinning up a VM and following along: swap the IPs and hostnames in the output for your own, the structure does not change. The reading column is the heart of this page -- **anyone can type a command; what is worth something is reading a conclusion out of the output**. The "next step" after each block tells you when a normal result means you are done, and where to branch off (and to which page) when it is not.

The scenarios build on one another: scenarios 1-3 walk the "local machine -> gateway -> remote host" connectivity chain, which matches the first half of the troubleshooting page; scenarios 4-6 go from ports and DNS down to packet capture, the deep dive for "it connects but the service is unusable"; scenarios 7-8 handle the two advanced cases of "connected but slow" and "connected but on the wrong path." Overview:

| Scenario | Question it answers | Core commands |
|------|-----------|----------|
| 1. Local configuration | Is this machine's network configuration correct | `ip -br addr`, `ip route`, `cat /etc/resolv.conf` |
| 2. Gateway reachable | Can I reach the gateway | `ping`, `ip neigh` |
| 3. Remote reachable | And beyond the gateway -- which hop is dropping packets | `ping`, `traceroute`, `mtr` |
| 4. DNS resolution | The IP works but the name does not | `dig`, `resolvectl` |
| 5. Port aliveness | Is this port alive | `ss`, `nc`, `curl -v` |
| 6. Capture as evidence | What is actually happening on the wire | `tcpdump` |
| 7. Latency and bandwidth | Connected but slow -- how do I read the numbers | `ping -c`, `iperf3` |
| 8. Actual path selection | Which path does my traffic take | `ip route get`, `ip rule` |

Install the tools up front in one go, so you never have to stop halfway through a diagnosis to fetch a package. Package names across the three families (`ip`/`ss` both come from iproute2, `ping` comes from iputils, and most distros ship them by default):

| ping/arping | `iputils-ping` | `iputils` (install `iputils-arping` for arping) | `iputils` |
| traceroute | `traceroute` | `traceroute` | `traceroute` |
| mtr | `mtr-tiny` (or `mtr`) | `mtr` | `mtr` |

## 1. Is This Machine's Network Configuration Correct

**Goal**: within thirty seconds, confirm the three basic facts about this machine -- address, routes, and DNS. Run the standard three probes first, and add one more look at the TX/RX counters when the physical layer is in doubt:

```bash
$ ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             192.168.56.101/24 fe80::215:5dff:fe00:1001/64
$ ip route
default via 192.168.56.1 dev eth0 proto static metric 100
192.168.56.0/24 dev eth0 proto kernel scope link src 192.168.56.101 metric 100
$ cat /etc/resolv.conf
# Generated by systemd-resolved; do not edit by hand
nameserver 127.0.0.53
options edns0 trust-ad
search example.lan
$ ip -s link show eth0
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT
    link/ether 08:00:27:c0:1a:2d brd ff:ff:ff:ff:ff:ff
    RX:  bytes    packets errors dropped overrun mcast
    RX:  1.2GiB     920k     0       3       0     12k
    TX:  bytes    packets errors dropped carrier collsns
    TX:  340MiB     610k     0       0       0       0
```

**Reading**: `ip -br addr` answers three things -- the state column must be `UP` (`UNKNOWN` is common on carrier-less or virtual interfaces and does not mean "configured"), addresses must carry a **prefix length** (only `/24` makes it a network number; without it `ip` refuses the input), and on a multi-NIC box, which interfaces actually hold addresses. `ip route` must contain a `default via` line: the IP after `via` is the gateway and `dev` is the outgoing interface, and both have to sit on the same "live" NIC. If `resolv.conf` points at `127.0.0.53`, a local systemd-resolved is standing in and the real upstream must be read from `resolvectl status` (see scenario 4); if it is an old-style hardcoded `nameserver 8.8.8.8` written by NetworkManager or by hand, resolution behavior is entirely determined by that line. The two counter columns of `ip -s link` are the physical layer's check-up sheet: non-zero `errors` usually means cable, optic, or driver trouble, and a climbing `dropped` usually means a small ring buffer filling up (VMs and high-PPS cases) -- the numbers only ever grow, so compare them against uptime to make the growth rate meaningful.

**Next step**: if all three lines are right, jump straight to scenario 2; if there is no default route, go to [Network Configuration Basics](./network-configuration.md) for persistent setup (pick one of NetworkManager / Netplan / networkd); if the interface is `DOWN`, run `ip link set eth0 up` first, then go back to the physical layer.

## 2. Can I Reach the Gateway

**Goal**: confirm layer two (the same broadcast domain) is healthy -- if the gateway does not answer, none of the later "the internet does not work" conclusions hold.

```bash
$ ping -c 3 192.168.56.1
PING 192.168.56.1 (192.168.56.1) 56(84) bytes of data.
64 bytes from 192.168.56.1: icmp_seq=1 ttl=64 time=0.412 ms
64 bytes from 192.168.56.1: icmp_seq=2 ttl=64 time=0.389 ms
64 bytes from 192.168.56.1: icmp_seq=3 ttl=64 time=0.401 ms

--- 192.168.56.1 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 0.389/0.401/0.412/0.010 ms
$ ip neigh show
192.168.56.1 dev eth0 lladdr 08:00:27:c0:1a:2d REACHABLE
```

**Reading**: `ttl=64` from a same-subnet gateway plus sub-millisecond latency shows a direct layer-two path; `ip neigh` showing the gateway MAC in state `REACHABLE` proves ARP completed -- **the hidden precondition for a successful ping is that the neighbor table holds this entry**. The state column of the neighbor table is a small state machine in its own right: `INCOMPLETE` means the ARP request just went out and nobody has answered yet, `REACHABLE` means reachability was confirmed recently, `STALE` means the confirmation period has passed but the entry remains (it is verified before next use), and `FAILED` means several rounds of asking went unanswered. During troubleshooting, map the symptom onto the semantics -- `FAILED` or a long-lived `INCOMPLETE` points at layer-two problems such as a mistyped IP, a gateway interface that is not up, or machines on the same subnet separated by a VLAN; `STALE` is entirely normal and is not a fault. Also glance at `ttl`: `ttl=64` means directly connected, `ttl=63` means a hop has already been crossed -- you are not pinging the address you think you are.

**Next step**: if it works, move to scenario 3; if not, run `ip route get <gateway-ip>` to confirm the outgoing interface and source address it would use, then check whether this machine's IP really is on the gateway's subnet (the commands from scenario 8 come in handy here).

## 3. What About Beyond the Gateway

**Goal**: separate "the remote host is dead" from "one hop along the path is dropping packets," using two layers of tools that cross-check each other.

```bash
$ ping -c 3 223.5.5.5
64 bytes from 223.5.5.5: icmp_seq=1 ttl=49 time=12.4 ms
...
--- 223.5.5.5 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss
$ traceroute -n 223.5.5.5
traceroute to 223.5.5.5 (223.5.5.5), 30 hops max, 60 byte packets
 1  192.168.56.1     0.389 ms  0.356 ms  0.341 ms
 2  10.0.0.1         3.156 ms  3.104 ms  3.071 ms
 3  223.5.5.5       12.402 ms 12.381 ms 12.360 ms
$ mtr --report -c 20 223.5.5.5
HOST: dev01                    Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 192.168.56.1            0.0%    20    0.4   0.4   0.3   0.7   0.1
  2.|-- 10.0.0.1                0.0%    20    3.2   3.3   3.0   4.1   0.3
  3.|-- 223.5.5.5               0.0%    20   12.4  12.5  12.2  13.0   0.2
```

**Reading**: `ttl=49` is a dozen lower than the gateway hop, which means several routers have already been crossed -- use it first to confirm "the remote host is alive and the path generally works." In `traceroute`, each line is one hop and each hop's three columns are the latencies of three probes; the hop where latency **steps up** is the link where the delay begins. A `*` only means that device does not answer ICMP time-exceeded, not that it is down. If ICMP is being rate-limited along the whole stretch, switch probe protocols: `traceroute -T -p 443 223.5.5.5` sends TCP SYNs instead (pick a target port the far end really has open) -- devices that stay silent to ICMP on the path usually answer TCP just fine; likewise `-I` forces ICMP and `-U` uses UDP. Momentary packet loss is unreliable; to locate a lossy segment use `mtr --report -c 20`: the `Loss%` column is that hop's probe loss rate, and **only the final row's Loss% represents the end-to-end result** -- a middle hop at 100% with a final row of 0% means that middle device is rate-limiting ICMP, not that the link is broken.

**Next step**: if everything passes, move to scenario 4; if the last row shows non-zero loss, use the segmented method in [Network Troubleshooting](./troubleshooting.md) to assign responsibility -- the local and gateway segments are already cleared by scenarios 1-2, so the blame falls on the carrier's path or the far end; when the far end is your own server, check `nstat`/`ss -s` and the NIC counters on the server side.

## 4. The IP Works but the Domain Name Does Not

**Goal**: split "the internet does not work" precisely into a resolution problem and a connectivity problem, isolating the variable with a single question:

```bash
$ dig @223.5.5.5 www.example.com
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41235
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
www.example.com. 86400 IN A 93.184.216.34

;; Query time: 18 msec
;; SERVER: 223.5.5.5#53(223.5.5.5)
$ dig www.example.com | grep -A1 'SERVER:'
;; SERVER: 127.0.0.53#53(127.0.0.53) (UDP)
$ getent hosts www.example.com
93.184.216.34   www.example.com
$ resolvectl status
Link 2 (eth0)
    Current Scopes: DNS
         DNS Servers: 192.168.56.1
          DNS Domain: example.lan
```

**Reading**: `@223.5.5.5` bypasses the local machine and asks a public resolver directly -- an IP in `ANSWER SECTION` with `status: NOERROR` means neither the name nor outbound port 53 is at fault, so the problem must be in this machine's resolution chain; the `SERVER:` line confirms where this answer came from, and that is always the first thing to check. In the second query, without `@`, `SERVER` lands on `127.0.0.53`, which means the local query was taken over by systemd-resolved; use `resolvectl status` to see which upstream it forwards to and whether the `DNS Domain` routing domain is steering your names to an internal resolver. Note the division of labor between `dig` and `getent`: **dig speaks only the DNS protocol, while getent walks the whole nsswitch chain** -- entries in `/etc/hosts` and the ordering of `files` ahead of `dns` are invisible to dig. When an application reports "a different answer than dig," first reproduce the application's view with `getent hosts`, then look at `/etc/hosts` and `/etc/nsswitch.conf`. Once the cache layer is confirmed as the culprit, `resolvectl flush-caches` clears the local cache and a retest closes the case.

**Next step**: upstream works but local fails -> fix the resolved configuration (reproduce hop by hop with `resolvectl query`); upstream fails too -> outbound UDP 53 is being blocked (retry with `@1.1.1.1`, and over TCP with `dig +tcp @223.5.5.5`); for internal problems with a self-hosted resolver, go deeper into [DNS Server (BIND)](../server/dns/bind.md); if the name resolves but the site will not open, jump straight to scenario 5.

## 5. Is This Port Alive

**Goal**: the server side confirms it is listening and the client side confirms reachability -- ask each viewpoint once, so you never go hunting on the far end for a cause that is local.

```bash
$ ss -tlnp
State  Recv-Q Send-Q Local Address:Port   Peer Address:PortProcess
LISTEN 0      511          0.0.0.0:80        0.0.0.0:*    users:(("nginx",pid=812,fd=6))
LISTEN 0      128          0.0.0.0:22        0.0.0.0:*    users:(("sshd",pid=640,fd=3))
$ ss -uln | head -3          # UDP listeners need their own query: no connection concept, -t hides them
State   Recv-Q SendQ Local Address:Port  Peer Address:Port
UNCONN  0      0     127.0.0.53%lo:53         0.0.0.0:*
$ ss -s                     # one-line global overview
TCP:   12 (estab 4, closed 6, orphaned 0, timewait 2)
$ nc -vz web.example.com 443
Connection to web.example.com (93.184.216.34) 443 port [tcp/https] succeeded!
$ nc -vz db.internal 5432
nc: connect to db.internal (192.168.56.201) port 5432 (tcp) failed: Connection refused
$ curl -v https://web.example.com/ -o /dev/null 2>&1 | grep -E 'subject:|SSL certificate|HTTP/'
*  subject: CN=web.example.com
*  SSL certificate verify ok.
< HTTP/1.1 200 OK
```

**Reading**: server-side `ss -tlnp` has three essentials -- the `LISTEN` state, the address:port format (`0.0.0.0` means listening on every NIC, `127.0.0.1` local only), and the process name in the `Process` column (it needs privileges to be visible). UDP services need `-uln` to show up (DNS, DHCP, and QUIC are all in that table, and the state column reads `UNCONN` rather than `LISTEN` -- UDP has no connection semantics); the global line from `ss -s` is the quick way to ask "is this machine's connection count abnormal." On the client side the two failure meanings are utterly different: `Connection refused` means **the far end actively sent an RST** -- no process is listening on that port, so the problem is the service itself; **hanging until timeout** means packets are being dropped in the middle -- firewall, ACL, or a routing black hole. After the handshake succeeds, `curl -v` keeps going into TLS and the HTTP layer, answering three questions at once: "the port is open, the certificate is right, and HTTP answers."

**Next step**: `refused` -> on the server, check the process and the listening address; timeout -> check the firewall (see [Firewall](../security/firewall.md)) and security groups; `nc` succeeds but the browser errors -> a certificate or Host header problem, look at `curl -v`'s certificate and response lines; for the TCP state machine and where RSTs come from, see [TCP/IP Essentials](./tcpip-essentials.md).

## 6. Capture a Real Session

**Goal**: when every reading tool refuses to give an answer, packet capture is the final evidence -- filter first, capture little, and save to a file for replay.

```bash
$ sudo tcpdump -i any -n host 93.184.216.34 and port 80 -c 20
tcpdump: listening on any, link-type LINUX_SLL2 (Linux cooked v2), capture size 262144 bytes
21:14:03.101245 eth0 In  IP 93.184.216.34.80 > 192.168.56.101.51234: Flags [S.], seq 1829301769, ack 3445189732, win 65483, length 0
21:14:03.101312 eth0 Out IP 192.168.56.101.51234 > 93.184.216.34.80: Flags [.], ack 1, win 501, length 0
21:14:03.101398 eth0 Out IP 192.168.56.101.51234 > 93.184.216.34.80: Flags [P.], seq 1:76, ack 1, length 75
$ sudo tcpdump -i any -n host 93.184.216.34 and port 80 -w capture.pcap -c 200
$ tcpdump -r capture.pcap -nn | head
$ tcpdump -r capture.pcap -nn 'tcp[tcpflags] & tcp-syn != 0'   # filter again on replay: SYN packets only
reading from file capture.pcap, link-type LINUX_SLL2 (Linux cooked v2)
21:14:03.101201 eth0 Out IP 192.168.56.101.51234 > 93.184.216.34.80: Flags [S], seq 3445189731, win 64240, length 0
```

**Reading**: `Flags [S.]` is SYN-ACK, `[.]` is a bare ACK, `[P.]` carries data -- pair the `In`/`Out` direction column with the handshake flags and the first three lines of a healthy session already show "I initiated it (or they did) and they answered." **An `Out` `[S]` with no matching `In` `[S.]` means the SYN was dropped**: this cross-confirms the timeout in scenario 5, and puts the responsibility on the path rather than the service. Always write the filter expression `host A and port 80` up front -- capturing everything and filtering afterwards is both dangerous and slow in production. BPF filters take effect **once at capture time and once at replay time**: use coarse conditions to scope the capture before `-w`, then finer conditions such as `tcp[tcpflags] & tcp-syn != 0` at `-r` replay, so the same pcap can be reviewed from any angle. Once it is saved, copy it back and open it in Wireshark (the GUI is far more comfortable for analyzing HTTP fragmentation, retransmissions, and windows than a terminal): use the command line for quick evidence and Wireshark for the deep post-mortem.

**Next step**: handshake succeeds but no HTTP response -> go to the server and read the application logs; repeated `[S]` retransmissions -> judge link quality with scenario 7; nothing captured at all -> confirm `-i` selected the right interface first (recheck with `ip -br addr`), because tunnels and virtual interfaces do not carry their traffic over the physical port.

## 7. How Much Latency and Bandwidth Are There Really

**Goal**: turn "it feels slow" into comparable numbers -- latency belongs to ping, bandwidth to iperf3, and they measure different things.

```bash
$ ping -c 10 223.5.5.5
--- 223.5.5.5 ping statistics ---
10 packets transmitted, 10 received, 0% packet loss
rtt min/avg/max/mdev = 11.982/12.410/13.015/0.312 ms
$ iperf3 -s                      # server (run it on the far-end machine)
$ iperf3 -c 192.168.56.200 -P 4  # client, 4 parallel streams
[SUM]   0.00-10.00  sec  4.98 GBytes  4.28 Gbits/sec  sender
        4.89 GBytes  4.20 Gbits/sec  receiver
$ iperf3 -c 192.168.56.200 -u -b 100M   # UDP, 100M packet rate
[  5]  0.00-10.00  sec   119 MBytes   100 Mbits/sec  0.047 ms  0/12800 (0%)
$ ping -c 3 -M do -s 1472 223.5.5.5   # MTU probe: 1500 minus 28 bytes of headers = 1472 payload, fragmentation forbidden
ping: local error: Message too long, mtu=1500        # some hop on the path has an MTU below 1500
```

**Reading**: in ping's quartet, `min` is the physical floor, `avg` is the normal case, and `mdev` is jitter -- **jitter exposes trouble earlier than the mean does** (a flaky Wi-Fi radio and queueing both show up in mdev first). iperf3's default TCP mode measures "how much throughput the application layer can squeeze out," limited by the congestion window and the bandwidth-delay product, so only `-P 4` parallel streams approach the link's ceiling; UDP mode `-u -b 100M` asks a different question -- "does it drop packets when hit at 100M" -- and the `0/12800 (0%)` loss line is the only number to watch. The two tools naturally disagree: low ping latency does not mean high bandwidth (a slow link still replies in milliseconds), and a saturated iperf3 run does not mean healthy latency (congestion queues push delay up) -- each measures one dimension, so read them together. The trailing `-M do -s 1472` is a handy MTU probe: payload plus 28 bytes of headers lands exactly on 1500 with fragmentation forbidden, so when the path MTU is too small the local machine reports `Message too long, mtu=...` outright, and binary-searching the payload size locates the path MTU. The classic mystic fault of "small packets pass, large packets die" (common with VPNs, tunnels, and PPPoE) is settled by one such test; the principle is set out in the MTU section of [TCP/IP Essentials](./tcpip-essentials.md).

**Next step**: UDP loss -> lower `-b` and binary-search the link's capacity; a single TCP stream cannot saturate it but multiple streams can -> normal (window/BDP limit, not a fault); large latency jitter -> rule out local CPU load (`mpstat`) and softirq activity (`/proc/interrupts`) first, then segment with mtr as in scenario 3; for the methodology, return to the performance section of [Network Troubleshooting](./troubleshooting.md).

## 8. Which Path Is My Traffic Actually Taking

**Goal**: on a multi-NIC, multi-uplink machine, "I configured a route" is not the same as "the traffic goes that way" -- ask the kernel directly what its routing decision is right now.

```bash
$ ip route get 1.1.1.1
1.1.1.1 via 192.168.56.1 dev eth0 src 192.168.56.101 uid 1000
$ ip rule show
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default
$ ip route get 1.1.1.1 from 192.168.57.10 iif eth1
1.1.1.1 from 192.168.57.10 iif eth1 lookup 100 via 192.168.57.1 dev eth1
```

**Reading**: `ip route get` gives three things at once -- the outgoing interface `dev`, the next hop `via`, and **the source address the kernel chose for this communication, `src`**. The third is the most often overlooked: on a machine with several addresses, which one an application sees as "where I send from" is decided here, so when SNAT rules or a far-end allowlist do not match, the first suspect is that `src` is not the address you assumed. Re-running with `from` and `iif` reproduces the routing result for "a packet from a given source arriving on a given interface" -- in the second command, `lookup 100` shows a policy routing table was hit rather than `main`. This kind of ingress routing behavior can only be probed by naming `from`/`iif` explicitly; a bare `ip route get` always answers only for flows this machine originates. `ip rule show` lists the routing policy priorities: the smaller the number, the higher the priority; the `local` table catches this machine's own addresses, and on most machines the list ends there -- if there are custom entries, the box has policy routing and tables other than `main` are in play.

**Next step**: `src` is wrong -> check the address configuration on that outgoing interface and the priority order in `ip rule`; confirm where a non-default exit goes -> rerun `ip route get` with `from <source-ip>`; for the full treatment of policy routing and multiple tables, see [Routing and NAT](../server/routing-nat.md).

## One-Page Quick Reference

Before wrapping up, compress the eight scenarios into a single table so you can reverse-look-up the first command from a symptom:

| Symptom | First command | Second command |
|------|----------|----------|
| Are address/route set correctly | `ip -br addr` | `ip route` |
| Gateway unreachable | `ping <gateway>` | `ip neigh show` |
| Internet unreachable | `ping <public-ip>` | `mtr --report -c 20 <public-ip>` |
| Name fails while IP works | `dig @8.8.8.8 <name>` | `getent hosts <name>` |
| Service refuses connections | `ss -tlnp` (server side) | `nc -vz <host> <port>` |
| Not sure packets are there | `tcpdump -i any -n` | `-w` to save and replay |
| Connected but slow | `ping -c 10` | `iperf3 -c -P 4` / `-u -b` |
| Doubtful which way traffic flows | `ip route get <target>` | `ip rule show` |

## Common Pitfalls

**The IP you see in ip addr is not necessarily the one in use -- source address selection on multi-NIC machines.** `ip -br addr` only lists what is configured, it never promises a flow actually uses it: the kernel picks `src` after routing. On multi-NIC boxes, always verify with `ip route get <target>` (scenario 8); when SNAT, firewall rules, or a far-end allowlist are written with the wrong source address, the root cause is usually here.

**A successful ping does not mean the port works -- ICMP and TCP are two different roads.** ICMP is a network-layer protocol, TCP is a transport-layer port service; ICMP succeeding only proves routing reachability, not that a process exists on the far end, and certainly not that the firewall allows TCP. To verify a service, always use scenario 5's `ss`/`nc`/`curl` trio.

**A `*` on the last hop of traceroute does not mean it is unreachable -- intermediate devices rate-limit ICMP.** When intermediate routers rate-limit or never send time-exceeded messages, that hop shows `*`, and even a whole run of `*` in the middle with a normal last hop is routine. Judge reachability only from the destination's echo (ping, or traceroute's last hop), and locate the lossy segment with `mtr --report`, reading the final row's `Loss%`.

**nc -z tests only the handshake, not the data layer.** `-z` closes right after establishing a connection; passing it does not mean the application works: a bad TLS certificate, a wrong HTTP Host, or failed authentication only surfaces after `-z`. So once `nc` succeeds, still run `curl -v` across the full application chain.

**iperf3 will not saturate with one thread -- -P for multiple streams and the default window.** A single TCP stream is limited by the congestion window and the bandwidth-delay product, so on high-bandwidth, long-latency links it can only use part of the capacity. Re-test with `-P 4` before drawing conclusions; only if it still falls short should you suspect the link or the far end. In UDP mode, do not forget to set `-b` explicitly, otherwise the default low rate never reveals the ceiling.

**dig asks DNS, not the CDN cache -- the IP you see varies by location.** The authoritative answer depends on CDN scheduling, so an A record you dig from inside the internal network legitimately differs from what a public user receives. To decide "is the resolution correct," query the authority directly with `@authority` (see [DNS Server (BIND)](../server/dns/bind.md)) and check the `SERVER:` line in `dig` output to confirm who was asked.

**pinging 127.0.0.1 does not mean the NIC works -- lo never touches the physical layer.** The loopback interface turns around inside the kernel; it answers even when the NIC is down or the cable is unplugged. To judge the physical link you must `ping` a real address on the far side and go back to scenario 1 for interface state and counters. The "my own service works locally but other machines cannot reach it" investigation should likewise start with "ping a different address" -- do not be fooled by loopback success.

**Hand-edited resolv.conf gets overwritten.** NetworkManager, systemd-resolved, and netplan may all rewrite `/etc/resolv.conf` after a reboot or reconnection; the satisfaction of editing it by hand does not survive a `systemctl restart`. The correct persistent entry points are the connection configuration (`nmcli`/netplan YAML) and the systemd-resolved configuration respectively -- after changing them, re-verify with scenario 4's chain. The "do not edit by hand" comment at the top of the file is not decoration.

## Verify It Yourself

A command only counts as familiar once you have **seen what its failure looks like** -- break something on purpose in your own lab, then fix it:

1. **Misconfigure the gateway**: point the VM's default route at a non-existent IP (`ip route replace default via 192.168.56.254`), walk through scenarios 1-3, confirm `INCOMPLETE` in the neighbor table and that the internet is dead while the gateway's own subnet still answers, then put it back.
2. **Stop a service**: after `systemctl stop nginx`, compare `Connection refused` from `nc -vz` on another machine against the timeout produced by a firewall DROP -- in tcpdump the two failures are "an RST came back" and "it sank without a trace."
3. **Create an MTU black hole**: add a VXLAN hop between two VMs, or drop an interface MTU to 1400, then binary-search the path MTU with scenario 7's `-M do -s`, and verify how it relates to the symptom of SSH logging in while `scp` of a large file hangs.
