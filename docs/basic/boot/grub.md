# The GRUB Bootloader

After the firmware hands control over to the disk, the component that actually moves the kernel into memory and hands it the kernel parameters you selected is the bootloader. In the Linux world it is almost always GRUB -- both Debian/Ubuntu and RHEL/CentOS/Rocky default to **GRUB2**, while Arch leaves the choice to the user (GRUB, systemd-boot, and rEFInd are all common). GRUB is a complete miniature operating system: it has a menu, a command line, can read ext4/Btrfs filesystems, and can address memory in 32-bit protected mode -- which is exactly why it is far more complex than the 446-byte stub of the old BIOS era.

The key to understanding GRUB is **layering**: what you normally edit is the "source" (`/etc/default/grub`, `/etc/grub.d/`), what the system executes is the "generated output" (`grub.cfg`), and what you often need to touch when a boot fails is the even lower-level "installation" (`grub-install` writing to the MBR or the ESP). Conflating these three layers produces the classic dilemmas: "I changed the config but it did not take effect" or "the boot is rescued but the menu is still broken." This page goes from structure to configuration, then gives a rescue workflow that works across all three families.

> Content adapted from the GNU GRUB manual, the Arch Wiki, and Bird's Private Recipes (Lin's Linux Administration Guide); see the references at the end.

## What This Page Covers

- Separate GRUB's two-stage loading structure (BIOS vs UEFI path differences)
- Understand the three layers of configuration
- Know the command differences for regenerating GRUB config and reinstalling GRUB across the three families
- Use the GRUB menu's `e` key to temporarily modify kernel parameters (the standard entry point into rescue / single-user mode)
- The full boot rescue workflow with Live USB + chroot, distinguishing the `grub-install` arguments for BIOS vs UEFI

## 1. GRUB's Two-Stage Structure

### BIOS/Legacy Path

1. **Stage 1: `boot.img`** -- written into the first 446 bytes of the MBR. It does exactly one thing: locate and load stage 2.
2. **Stage 2: `core.img`** -- usually in the gap right after the MBR, or in a BIOS Boot partition (a small partition reserved for it on GPT disks). `core.img` contains filesystem drivers, can read the modules under `/boot/grub/i386-pc/`, eventually loads `normal.mod`, and parses `grub.cfg`.
3. Once `grub.cfg` is read, GRUB shows the menu. The selected entry reads the kernel (`vmlinuz-*`) and initramfs (`initrd.img-*`) into memory, then jumps to the kernel entry point.

### UEFI Path

1. The firmware follows the NVRAM boot entry to find the `.efi` file in the ESP (usually `\EFI\<distro>\grubx64.efi`, or relayed through `shimx64.efi`).
2. That `.efi` file is itself a complete GRUB (EFI version); it reads `grub.cfg` from the ESP or from `/boot/grub/`.
3. From here it matches the BIOS path: menu -> load kernel/initramfs -> kernel starts.

The **common endpoint** of both paths is `grub.cfg` and the kernel image; the divergence is only in "who reads it." Understanding this tells you what to fix separately during a rescue: on BIOS you repair the MBR/`core.img`, on UEFI you repair the `.efi` file and the NVRAM entry in the ESP.

```bash
$ ls /boot/grub/     # Debian/Ubuntu, Arch; RHEL family uses /boot/grub2/
grub.cfg  fonts  grubenv  locale  x86_64-efi/  i386-pc/
```

## 2. The Three Layers of Configuration

GRUB's configuration is **generated**, and this is where the biggest pitfalls lie:

| Layer | Location | Should you edit it? |
|-------|----------|---------------------|
| User variables | `/etc/default/grub` | Daily edits go here (timeout, default entry, kernel parameters) |
| Menu generation scripts | `/etc/grub.d/*` | Advanced use (custom menu entries, dual-boot detection) |
| Final configuration | `/boot/grub/grub.cfg` or `/boot/grub2/grub.cfg` | Never edit; changes get overwritten anyway |

The header of `grub.cfg` literally says "DO NOT EDIT THIS FILE" -- it is generated by `grub-mkconfig`, which calls the scripts under `grub.d` and reads `/etc/default/grub` to aggregate the result. The correct workflow is always: edit the source -> regenerate -> verify.

```bash
$ cat /etc/default/grub
GRUB_DEFAULT=0                  # Default menu entry index (0 = the first); can also be a submenu string
GRUB_TIMEOUT=5                  # Seconds the menu stays; 0 boots the default entry immediately (hides the menu)
GRUB_DISTRIBUTOR="Ubuntu"       # Distribution name shown in the menu
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"   # Parameters appended to normal boot entries
GRUB_CMDLINE_LINUX=""           # Parameters appended to all entries (including recovery)
GRUB_DISABLE_OS_PROBER=false    # Whether to probe for Windows/macOS to generate menu entries
```

The difference between `GRUB_CMDLINE_LINUX_DEFAULT` and `GRUB_CMDLINE_LINUX`: the former applies only to normal boot entries (put "everyday parameters" like `quiet splash` here), while the latter applies to all entries including recovery mode ("hard parameters" like `root=/dev/sda2` are written automatically by the installer).

Example modification -- change the default boot entry to the 2nd one and turn off `quiet` for easier troubleshooting:

```bash
$ sudo sed -i 's/GRUB_DEFAULT=0/GRUB_DEFAULT=1/' /etc/default/grub
$ sudo sed -i 's/GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"/GRUB_CMDLINE_LINUX_DEFAULT=""/' /etc/default/grub
```

Scripts under `/etc/grub.d/` execute in numeric filename order. The common ones:

| Script | Purpose |
|--------|---------|
| `00_header` | Reads `/etc/default/grub`, generates general settings (theme, timeout, module loading) |
| `05_debian_theme` | Background image / fonts (Debian/Ubuntu) |
| `10_linux` | **Scans `/boot` for kernels and generates the Linux menu entries** (the most critical) |
| `30_os-prober` | Probes for other operating systems (Windows, other distros) |
| `40_custom` | Reserved for user-written menu entries; preserved on every regeneration |

## 3. Regeneration and Reinstallation (Three-Family Comparison)

**Regenerating the configuration** (mandatory after editing `/etc/default/grub`):

```bash
# Debian/Ubuntu
$ sudo update-grub
Sourcing file `/etc/default/grub'
Found linux image: /boot/vmlinuz-6.8.0-45-generic
Found initrd image: /boot/initrd.img-6.8.0-45-generic
Found Windows Boot Manager on /dev/sda1@/EFI/Microsoft/Boot/bootmgfw.efi
done

# Arch (explicitly specify the output path)
$ sudo grub-mkconfig -o /boot/grub/grub.cfg

# RHEL/CentOS/Rocky (both the binary and the path carry a 2)
$ sudo grub2-mkconfig -o /boot/grub2/grub.cfg
```

**Reinstalling GRUB itself** (when boot code is corrupted, the disk was swapped, or during a chroot rescue) -- this is the step that actually "writes the MBR" or "writes the ESP":

```bash
# BIOS/Legacy: write to the MBR of the whole disk (note: the disk, not a partition)
$ sudo grub-install /dev/sda

# UEFI: write to the ESP and register a boot entry in NVRAM
$ sudo grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=GRUB
#   --efi-directory: ESP mount point (on Arch, if the ESP is mounted at /boot, use /boot instead)
#   --bootloader-id: directory name after EFI/ on the ESP, also the NVRAM entry display name

# RHEL family (command names carry a 2)
$ sudo grub2-install /dev/sda                                      # BIOS
$ sudo grub2-install --target=x86_64-efi --efi-directory=/boot/efi # UEFI
```

**Common pitfalls**:

1. **Omitting `--efi-directory` under UEFI** -- GRUB defaults to looking for `/boot/efi`; if your ESP is mounted at `/boot` (a common Arch layout) it installs to the wrong location, and after reboot the NVRAM points at a file that no longer exists.
2. **Passing a partition instead of a disk to `grub-install`** -- in BIOS mode you pass `/dev/sda` (the disk), not `/dev/sda1` (a partition). Getting it wrong usually reports `this utility will not install grub to one of your platform firmware` or silently installs to the wrong location.
3. **Regenerated `grub.cfg` but never ran `grub-install`** -- you only fixed the menu, not the boot code, so the machine still stops at the `grub>` prompt or `no bootable device`.
4. **Using `update-grub` on Arch** -- that command is a Debian-specific script; Arch does not have it, you just get `command not found`. On Arch, always use `grub-mkconfig -o ...`.

## 4. Temporarily Modifying Kernel Parameters (Press `e` in the GRUB Menu)

A troubleshooting entry point that requires no config file changes and takes effect immediately on the next boot: when the GRUB menu appears, press `e` to enter edit mode, find the line starting with `linux` (or `linuxefi`/`linux16`), append parameters at the end of the line, then press `Ctrl+X` (or F10) to boot with the modified parameters.

```text
linux   /boot/vmlinuz-6.8.0-45-generic root=UUID=... ro quiet splash $vt_handoff
# ^ Move the cursor to the end of the line, append systemd.unit=rescue.target after a space, then press Ctrl+X to boot
```

Common rescue parameters:

| Parameter | Purpose |
|-----------|---------|
| `systemd.unit=rescue.target` | Rescue mode (single user + networking off; requires the root password) |
| `systemd.unit=emergency.target` | Emergency mode (minimal environment; used after an initramfs-stage failure) |
| `init=/bin/bash` | Boot straight into bash as PID 1 (**no password required**; fix fstab/sudoers afterwards) |
| `systemd.unit=multi-user.target` | Skip the graphical interface (get to a tty when the Xorg driver is broken) |
| `ro` -> `rw` | Force the root partition to be mounted read-write (when read-only blocks file edits) |
| `rd.break` (RHEL-family initramfs) | Stop before the real root is mounted; used to change the root password |

**The standard path for changing the root password (same idea across all three families)**: press `e` in the GRUB menu -> append `rw init=/bin/bash` at the end of the `linux` line -> `Ctrl+X` into a root shell -> `mount -o remount,rw /` (skip if already rw) -> `passwd root` -> `exec /sbin/init` or just reboot. This chain does not depend on knowing the old password, and it is also why physical access is a security boundary -- locking the server room and setting a BIOS password are both about plugging the "physical access = highest privilege" hole.

After editing the menu, **this only takes effect for this one boot**; to make it permanent you still need to edit `/etc/default/grub` and regenerate.

## 5. Boot Failure Rescue Workflow (Live USB + chroot)

Applicable scenarios: boot stops at the `grub>` prompt, `error: no such partition`, `kernel panic - not syncing: VFS: Unable to mount root fs`, or there is simply no boot entry in NVRAM at all.

The skeleton shared by all three families is below; the differences concentrate in the command names and paths for `grub-install` / config regeneration:

```bash
# ---- 1. Boot from Live USB, confirm the disk layout ----
$ lsblk -f              # Assume sda1 = ESP (FAT32), sda2 = ext4 root partition

# ---- 2. Mount the root partition ----
$ sudo mount /dev/sda2 /mnt

# ---- 3. Mount the ESP (mandatory for UEFI rescue; on Arch commonly /mnt/boot) ----
$ sudo mount /dev/sda1 /mnt/boot/efi

# ---- 4. Bind-mount the virtual filesystems ----
$ sudo mount --bind /dev  /mnt/dev
$ sudo mount --bind /proc /mnt/proc
$ sudo mount --bind /sys  /mnt/sys
$ sudo mount --bind /run  /mnt/run

# ---- 5. Enter the chroot (from here on / is the original system root) ----
$ sudo chroot /mnt

# ---- 6a. BIOS: reinstall to the disk MBR (RHEL family uses grub2-install) ----
grub-install /dev/sda

# ---- 6b. UEFI: reinstall to the ESP (on Arch, if the ESP is mounted at /boot use --efi-directory=/boot) ----
grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=GRUB

# ---- 7. Regenerate the config (pick one per distro) ----
update-grub                                # Debian/Ubuntu
# grub-mkconfig -o /boot/grub/grub.cfg     # Arch
# grub2-mkconfig -o /boot/grub2/grub.cfg   # RHEL/CentOS/Rocky

# ---- 8. If the kernel is damaged too, rebuild initramfs (one per family) ----
# update-initramfs -u / mkinitcpio -P / dracut --force

# ---- 9. Exit and reboot ----
exit
sudo umount -R /mnt
sudo reboot
```

**Deciding between 6a and 6b**: go back to step 0 -- if `ls /sys/firmware/efi` exists in the Live environment, the firmware is UEFI, so use 6b; if it does not exist, use 6a. You can also check whether an ESP exists (a FAT partition with a GUID like `c12a7328-...` is almost certainly UEFI).

**Fixing only the NVRAM without rewriting files**: if `efibootmgr -v` shows the GRUB entry still exists, just with the order wrong, you do not need chroot at all -- just `sudo efibootmgr -o` to fix the order. The depth of a rescue should match the layer that is broken -- first locate the problem with read-only commands, then decide which layer to touch.

## 6. Three-Family Differences at a Glance

| Topic | Debian/Ubuntu | Arch | RHEL/CentOS/Rocky |
|-------|---------------|------|-------------------|
| Default bootloader | GRUB2 | **user's choice** (GRUB / systemd-boot / rEFInd) | GRUB2 |
| Config source | `/etc/default/grub`, `/etc/grub.d/` | same as left (GRUB); systemd-boot uses plain-text entry files | `/etc/default/grub`, `/etc/grub.d/` |
| Generated config | `/boot/grub/grub.cfg` | `/boot/grub/grub.cfg` | `/boot/grub2/grub.cfg` |
| Regenerate | `sudo update-grub` | `sudo grub-mkconfig -o /boot/grub/grub.cfg` | `sudo grub2-mkconfig -o /boot/grub2/grub.cfg` |
| Reinstall (BIOS) | `grub-install /dev/sda` | `grub-install /dev/sda` | `grub2-install /dev/sda` |
| Reinstall (UEFI) | `grub-install --target=x86_64-efi ...` | same as left, mind `--efi-directory` | `grub2-install --target=x86_64-efi ...` |
| Typical ESP mount point | `/boot/efi` | `/boot` (the ESP used directly as `/boot`; the Wiki recommendation) | `/boot/efi` |
| initramfs tool | `update-initramfs` | `mkinitcpio` | `dracut` |
| Dual-boot menu probing | `os-prober` (called automatically by `update-grub`) | you must `pacman -S os-prober` yourself and enable it in `grub.d` | `os-prober` (called automatically by `grub2-mkconfig`) |

## 7. Common Pitfalls

1. **Edited `/etc/default/grub` but the menu did not change**. You forgot to regenerate. Editing the source is always only the first step; `update-grub` / `grub-mkconfig` / `grub2-mkconfig` is the "commit."

2. **Editing `grub.cfg` directly**. The next regeneration overwrites it, and the file header already warns you. Edit the source or `40_custom` instead.

3. **During a rescue, `grub-install` cannot find the EFI variables or directory**. Usually the ESP was not mounted after chroot, or the `--efi-directory` path does not match the actual mount point. First confirm inside the chroot with `mount | grep efi` and `ls /boot/efi`.

4. **On Arch the ESP is mounted as `/boot`, but you copy Debian's `/boot/efi` path**. Both places must line up: the mount point, `--efi-directory`, and the output path of `grub-mkconfig -o`.

5. **`GRUB_TIMEOUT=0` hides the menu and blocks the rescue-parameter entry point**. Frantically press `Shift` at boot (BIOS) or `Esc` (some UEFI/GRUB builds) to force the menu to appear; or temporarily set `GRUB_TIMEOUT=3` and regenerate.

6. **Ran `grub-install` but not `grub-mkconfig`** (or the other way around). The former fixes the "bootloader itself," the latter fixes the "menu contents"; boot failures often involve both layers, and a rescue needs both steps.

7. **Btrfs root with multiple subvolumes, `root=` pointing at the wrong thing**. In `grub.cfg`, `root=UUID=...` must point at the **subvolume** (e.g. `@`), not the top-level device. Cross-check with `cat /etc/fstab`; getting this wrong during a rescue makes the kernel panic at the root-mount stage.
