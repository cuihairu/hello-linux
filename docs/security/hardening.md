# Hardening

Hardening is the process of shrinking the attack surface by configuring and tuning the system. If the firewall is the guard at the door and intrusion detection is the surveillance camera, then hardening is **reducing the number of doors and windows on the house itself, tightening key management, and locking the valuables in a safe** -- it adds no new features, yet it determines how much pressure falls on the two layers of defense in front of it. This page provides a reviewable baseline: minimal installation, redundant service cleanup, patch cadence, SSH hardening, kernel parameters, and the default mandatory access control (MAC) differences across the three distro families.

> Content draws on CIS Benchmarks, the Arch Wiki, Bird's Private Recipes (Lin's Linux Administration Guide), and each distro's security documentation -- see the references at the end.

## Introduction

A server in the state of "default install + unpatched + SSH password login + every port open" survives on the public internet for an average of minutes. Most serious security incidents need no exquisite technique from the attacker -- just three things lined up: **a large exposed surface (many ports/services), known vulnerabilities left unpatched (patch lag), and weak authentication (weak passwords/direct root login)**. Hardening is about dismantling those three pillars one by one. The three pillars also mark the boundary with the earlier chapters of this security section: the firewall only partially mitigates "exposed surface," and intrusion detection cannot claim "early detection" until all three pillars are addressed, which is why hardening comes before detection -- **first shrink what can be exploited, then talk about placing sensors on what remains**. Each pillar also has its own "looks solved but is not" illusions: a firewall installed with the wrong zone, patches applied but no reboot, keys configured while `PasswordAuthentication` is still yes -- **much of the latter half of this page is spent dismantling these illusions.**

It is also the convergence point for the preceding chapters: firewall policy, SSH keys, and detection tools can be configured perfectly well, but without periodic review and a unified baseline document they all drift over time -- a port opened by a new colleague, an account left behind by temporary debugging, a kernel that has not been rebooted in half a year are all textbook "configured once, no longer in effect." **Hardening is not a one-time project; it is a checklist you come back to and reconcile against after every change.** Treat "drift" as the default outcome, and every institutional design that follows (inventory, SLAs, archiving, drills) becomes necessary; assume configuration keeps itself correct, and this entire page can be deleted.

"Drift" deserves one more sentence, because it explains why the industry turns hardening into repeatable audit checklists like CIS Benchmarks: a security configuration is accurate the moment it is built, and then every emergency launch, every temporary allow granted by a new hire, every "let it run like this for now" exception pushes it away from baseline. For a team with no revisit mechanism, the actual security level is a decreasing function of time. The inventory commands at the end of each section exist precisely to install a periodic reset button on that decreasing function -- **a monthly sweep run once beats a yearly grand "security special campaign" as a rhythm of genuinely effective hardening.** The decreasing-function framing can be pushed one step further: drift not only lowers the security level, it raises the **cost of understanding** -- six months later nobody can explain where a rule came from, so nobody dares change it or delete it, exceptions pile up; that is what "institutional idling" looks like on a filesystem.

The division of labor between hardening, firewall, and intrusion detection is worth pinning down once more so the boundaries do not blur as you read: the firewall decides **which traffic can reach a process**, intrusion detection answers **what anomaly happened after it reached the process**, and hardening decides **how much exploitable surface the process and system itself have left**. No single layer, pushed to its limit, can plug the holes of the other two -- which is why the security chapter is ordered this way, and why the section 9 practice checklist chains the three layers' actions into one execution line. If you must hold all three in one sentence: the firewall governs "whether they get in," hardening governs "how usable things are once they are in," detection governs "whether you know after they have used it."

For reading, treat this page as **two-pass material**: the first pass reads through to build the framework, focusing on the "why" and the tables at the start of each section; the second pass reads only the section 9 checklist, executing against a VM and jumping back to the relevant section for commands whenever stuck. The classic failure mode with hardening material is "it all made sense when I read it, steps still got missed at go-live" -- **the execution path must be short enough to memorize**, which is why section 9 is deliberately written as a printable checklist rather than yet another narrative essay. On the second pass, take the trouble to adapt the checklist to your machine: drop the items that do not apply, add the services unique to you that your inventory turned up -- **a checklist that can be modified gets used; one that cannot only gets worshipped.**

A configuration item you cannot explain means the inventory is not finished yet.

The mapping between the six goals and the sections is: goal 1 -> sections 1-2, goal 2 -> section 3, goal 3 -> section 4, goal 4 -> section 5, goal 5 -> section 6, goal 6 -> section 7; sections 8 and 9 are respectively the anti-example list and the synthesis. I usually read it through once, then print section 9 out as a go-live checklist -- the right way to use a hardening page is "read once to build understanding, then only consult the tables," not reread the whole text at every launch. Behind the six goals runs one through-line: **everything read-back-able (`sshd -T`, `sysctl --system`, `getenforce`) must be read back, and everything irreversible (turning off SSH, enabling the firewall, luks-style formatting) requires an escape channel first** -- every step's acceptance in the nine steps of section 9 is essentially picking one half from each of those two sentences.

In the acceptance criteria, "explaining the reason" weighs more than "finishing the steps," because the failure mode of hardening is usually **configuration still there, intent already lost**: six months later nobody knows whether `AllowUsers ops deploy` is a business requirement or the residue of some incident, so nobody dares change it and nobody dares delete it, and exceptions pile up. The archived document of step 9 gives every configuration item a "birth certificate" -- it is the final link that elevates "operations" into "institution" on this page, and of the six goals it is the most easily skipped yet most decisive for long-term effect. If the six goals were written as team OKRs, the last one (Lynis self-check + remediation tracking) should be the only one with a recurring cadence: **the first five are projects, the sixth is operations** -- projects end; only operations can speak of a baseline.

## 1. Minimal Installation: The Attack Surface Starts Shrinking at Install Time

The first step of hardening is not in a config file but in the **install image and package selection**: every parameter tightened later is a patch on what has already been installed, while what installation decides to "not install at all" means the corresponding vulnerability never even enters the list. **Every extra package installed is another body of code that needs patching; every extra service started is another entrance that can be broken into.** Minimalism is not a "less is better" obsession -- it keeps "what is on this machine" in an enumerable, explainable state. Consider a counter-example: an "all-capable server" built from the full component set of twenty-year-old documentation, where nobody can fully answer "will turning this service off break the business" -- so every suspicious service stays, the attack surface equals the default-install full set, and the patch window keeps getting postponed for fear of touching the business. Enumerability is itself a security property. Writing it into acceptance criteria also works: **inventory questions should be answerable without logging into the machine, from the inventory in the repo alone** -- answers that require on-site digging mean the inventory is not yet the source of truth.

The three families do not start equal on "minimal"; understanding the differences sets realistic expectations: Debian's `--no-install-recommends` and `dnf groupinfo "Minimal Install"` give an official entry point to a minimal set; Arch's base group is already restrained, and the real bloat usually comes from later casual `pacman -S` installs; Ubuntu Server and Debian Server defaults are not fully identical either -- **the same hardening checklist produces visibly different inventories on the two**. When setting a baseline, pin down "the official minimal set for this role" first, then talk about additions, or every inventory will treat distro defaults as business needs. Conversely, do not misread "minimal" as "fewer is safer at any business cost" -- trimming away security dependencies like log rotation and time sync trades an operational outage for a fake security score. The criterion for minimalism is always **reverse exclusion from the business spec**, not a package-count leaderboard.

```bash
sudo apt install --no-install-recommends nginx   # Debian/Ubuntu: pulls in fewer extras
pacman -Q --explicit | sort > /tmp/explicit.txt  # Arch: the explicitly installed list
sudo dnf groupinfo "Minimal Install"             # RHEL family: the Minimal group
```

Arch's `pacman -Q --explicit` lists **manually installed** packages (dependencies excluded) -- the most ready-made "why is this installed on this machine" answer of the three families; the Debian side has `apt-mark showmanual`, the RHEL side `dnf repoquery --userinstalled`. Memorize the three-family mapping or you will miss things when replicating a baseline across distros. The inventory list best lives in a config repo: every time a new package is installed, diff "what appeared and why," and install decisions gain an audit trail -- **on a server with no inventory, three months later nobody can say which packages the business needs and which were left behind by some troubleshooting session**. The list file itself is best maintained as three columns, "package name + reason for install + date," rather than a bare package list -- a bare list answers only "what is there," while a list with reasons answers the three-part question at the start of section 1.

The action after inventory is a three-step: **remove what is not needed, disable what is not running, record what stays and why**. Typical cleanup targets are desktop/office suites (printing, Bluetooth, multimedia) and legacy protocols (telnet, rsh -- plaintext transports whose equivalent capability SSH covered long ago). Of the three, "record what stays and why" is the most skipped yet the most decisive for maintainability six months later: what got deleted can be reinstalled from the repo next time, **but what stays without a reason drags you back into the "should this be deleted or not" loop at the next inventory**.

```bash
sudo apt purge telnet rsh-client rsh-server      # Debian/Ubuntu
sudo pacman -Rns bluetooth-printer               # Arch: delete the config along with it
pacman -Qdtq | sudo pacman -Rns -                # clean orphan dependencies (check the list first!)
sudo dnf remove telnet rsh-server                # RHEL family
```

The "record what stays and why" step of cleanup is often skipped as bureaucracy, but it is really an interface left for future troubleshooting: six months later someone asks "why does this machine still have chrony," and the answer is "NTP is a dependency of timestamps and certificate verification; disabling it triggers a chain of problems" -- with that record, the question closes in thirty seconds; without it, a dependency analysis has to be redone. One line in the reason column is enough (what depends on it, a compliance requirement, a compatibility item not yet migrated); keep it in the config repo in the same file as the package list, and inventory diffs naturally review the reasons along with the packages.

A practical reverse self-check: run `ss -tulnp` for listening ports -- **every LISTEN should be able to answer "why is it on this machine."** Whatever cannot answer gets its service turned off, or at least gets blocked by the firewall (see [Firewall](./firewall.md)). The benefit of minimalism is more than a few fewer patches: with fewer packages, the change surface of `pacman -Syu`/`apt upgrade` shrinks, and the odds of a late-night automatic upgrade blowing up the business fall with it -- **attack surface and change risk are two faces of the same body of code**; narrowing it pays twice.

One more easily skipped discipline is **converging installation sources**: official repos only by default; third-party PPAs, script installs outside the AUR, and `curl | bash` style "one-click deployments" all require separate review. Every repo you introduce is that repo's signing key and build chain being trusted into your system -- when something goes wrong, what you uninstall is not just software but also your endorsement of that trust chain. Arch users owe the AUR this awareness in particular: the AUR is community recipes, not official packages; mark AUR packages separately in a `pacman -Q --explicit` inventory and evaluate their upgrade path apart from official packages. **The endpoint of minimalism is not "fewest packages" but "every remaining package can state its repo, version, and purpose."**

## 2. Service Shutdown and Least Privilege

Section 1 collected "what is installed on disk"; this section collects "**who can do what once things are running**" -- services, accounts, and sudo, three entrances, any one of which being too wide discounts section 1's work: a shared account with `NOPASSWD:ALL` can reinstall the full set within five minutes no matter how cleanly packages were removed. The three entrances also correspond to three different audit objects: services reconcile against `ss -tulnp`, accounts require reading `/etc/shadow` and group memberships, and sudo means digging through privilege-escalation logs -- **the more scriptable the inventory command, the less likely this baseline is to fail with personnel changes**, which is why this section's commands were all chosen for one-line, grep-able output. If section 1 is "warehouse inventory," this section is "access control and key inventory": however clean the warehouse, everyone holding a master key means there is no access control at all. The two sections together answer only two questions: **is the code still there, and who can touch it** -- a security review that fails to ask both usually produces nothing more than the words "hardened."

Tightening services and accounts shares one discipline: **observe before deleting, leave a trace before changing**. Before stopping a service, record the key fields of `systemctl show`; before deleting an account, lock it with `usermod -L` and observe for a cycle; before adjusting sudo rules, back up the `sudoers.d` directory -- these actions add no security strength, but they drop the rollback cost of "changed it wrong" from "reinstall from documentation" to "restore one file." High-risk operations are dense in the hardening phase; rollback plans should appear in pairs with the configuration commands, not be improvised after something breaks. There is no standard answer for the observation window's length, but it must be **long enough to cover one business cycle** (at least one release, one log rotation); otherwise "no problems observed" may just mean "the scenario where problems appear has not come around yet." The disposition at the end of the observation window must also leave a trace: **"keep it and write down why" and "delete it when due" are both legitimate conclusions; "forgot about it" is not** -- make the observation window a ticket with a due date so it does not quietly become a permanent allowlist.

The three subsections (services, accounts, sudo) can also be read ordered by an attacker's view: an attacker who gets in via SSH first looks at **which accounts you have to ram** (2.2's passwords and lockout), then, once in, at **how high sudo escalates** (2.2's allowlists), and only last at **what other services on the machine allow lateral movement** (2.1's LISTEN list). Hardening in that order means raising the price on each path from cheapest to most expensive -- **raising the bar on the cheapest route first is always the best value.** If only one thing can be prioritized, the answer for most internet-facing machines is 2.2's passwords and sudo: it raises both of the two most common paths (brute force and privilege escalation) at once, while 2.1's service cleanup only pays off fully once the attacker has already reached the intranet.

### 2.1 Redundant Services

The service list is the attack surface's runtime projection: binaries not on disk cannot be exploited, installed-but-not-running ones are at most a patch burden -- **only what is actually LISTENING engages the enemy**. So the cleanup order is always "stop what is running, then disable autostart, then decide whether to uninstall" -- three steps covering three different exposure dimensions. That order also matches troubleshooting instinct: first stop the traffic (immediate surface reduction), then stop the reboot from resurrecting it (so it does not come back after the maintenance window), and only then touch the disk (slowest and least reversible).

Disabling services has a side effect that is easy to overlook: **the log and monitoring points that depend on them disappear too**. After cups is turned off, printing alerts no longer firing is normal; but accidentally disabling auditd or a log-forwarding agent silently dismantles the detection stack -- so the cleanup list must distinguish "business services" from "security services"; the latter are not on the shutdown candidate list by default unless you can name the replacement.

`systemctl` separates "running" and "enabled at boot" -- check both when cleaning:

```bash
systemctl list-units --type=service --state=running --no-pager
sudo systemctl disable --now cups avahi-daemon bluetooth
```

The three families' defaults affect your starting point: the RHEL family ships fewer services out of the box but runs firewalld/auditd (both are security assets -- do not turn them off); Ubuntu Desktop brings a string of printing/Bluetooth/desktop services, while the server edition brings far fewer; Arch has the cleanest baseline, and **every service you manually installed with `pacman -S` is yours to clean up**. The criterion is uniform: **a service absent from this machine's business spec gets disabled and observed first, not "kept just in case."**

When cleaning services, also distinguish the applicable scenes of "disable" versus "uninstall": `disable --now` suits the observation window of "the business may still need it; stop it first to cut exposure," and it can be pulled back instantly if something breaks; `purge`/`-Rns` suits components confirmed unused, wiping their config files off the disk so that "the service is stopped but a weak default still sits in its config, waiting for an accidental start" cannot happen. The recommended rhythm is to disable and observe for one or two change cycles, then purge once no business dependency is confirmed -- **purging directly risks a dependency inversion** (some component you never noticed uses this package as a library), while keeping it forever risks carrying a pile of useless attack surface through the next full upgrade.

One more class of status in `systemctl` output is often ignored: `masked` (forced off by linking to `/dev/null`) is harder than `disabled` and suits services this machine should never run -- `bluetooth.service` or `cups.service` on a server. Consistent with the thinking behind locking sensitive files with `chattr +i`, **use masked for high-risk redundant services and disabled for reversible ones**, allocating the two strength levels by "the cost of an accidental start."

### 2.2 Accounts, sudo, and Password Policy

Least privilege starts with accounts: clean out stale accounts, tighten sudo, and set password quality and expiry policy. Account-layer problems show up in incident postmortems at a very high frequency -- they depend on no vulnerability, only one "it was convenient at the time" exception: shared root, permanent sudo for a contractor, a default password left on a demo environment. Treating accounts as assets lowers the real intrusion success rate more than installing another IDS. Accounts and the firewall are isomorphic in control theory: both are **allowlist + default deny**, differing only in that the firewall blocks the network 5-tuple while accounts block "who may exist under what identity after login" -- picture section 2's cleanup as the account-layer `default drop` and the intuition falls into place. Account inventory can add a time dimension: **every account needs a "birth date" and a "next review date"** -- an allowlist without review dates grows without bound, exactly like stale firewall rules.

```bash
sudo awk -F: '($2==""){print $1}' /etc/shadow   # normally there should be no output
# /etc/login.defs: PASS_MAX_DAYS 90 / PASS_MIN_DAYS 7 / PASS_WARN_AGE 14
```

Password quality is handled by PAM's pwquality module; the package names differ across the three families -- one of the most common sticking points in cross-distro configuration:

```bash
sudo apt install libpam-pwquality    # Debian/Ubuntu
sudo pacman -S libpwquality          # Arch
sudo dnf install libpwquality        # RHEL family (usually already installed)
# /etc/security/pwquality.conf: minlen = 12, all credit values = -1
```

On the sudo side, prefer "command allowlist + audit log" over everyone getting `ALL=(ALL) NOPASSWD:ALL`. **You must edit with `visudo -f`** (example below) -- a syntax error in `/etc/sudoers` takes out all sudo at once, precisely when you need sudo to fix it, one of the most destructive single-point mistakes in the hardening phase; `visudo` syntax-checks before saving, making it the only safe editing entry. Account lockout policy is not uniform across the three families: the RHEL family has `pam_faillock` available by default, with `faillock --user` to view/unlock; Debian/Ubuntu and Arch do not enable system-level lockout by default and usually leave IP banning to Fail2Ban (see [Intrusion Detection](./intrusion-detection.md)). When unsure whether the lockout module is enabled on your machine, read the relevant file under `/etc/pam.d/` to confirm instead of copying cross-distro snippets.

The granularity of the command allowlist also matters: giving the ops group `systemctl restart/status nginx` is an order of magnitude safer than `systemctl *`, and an order of magnitude more efficient than "you must find root" -- **the design goal of sudoers is not to eliminate privilege escalation but to narrow the escalation paths to a few auditable ones**. The companion `Defaults logfile` writes every escalation into `/var/log/sudo.log`; afterwards, reconciling it against auditd's identity events answers "who restarted nginx last night." The allowlist entries themselves need periodic review: sudo rules left over after a business retires are the same kind of liability as zombie ports in a firewall.

Account inventory has three more corners that are often missed, each worth a scan during cleanup. First, **empty-password lines**: the output of `awk -F: '($2=="")'` must be empty on a healthy system; any hit is a top-severity alert. Second, **non-root accounts with uid 0**: `awk -F: '$3==0'` should show exactly one line, `root` -- the first thing an attacker adds after escalating is a second uid 0. Third, **privileged accounts without expiry policy**: `chage -l ops` for `Password expires`/`Account expires`; a shared ops account set to "never expires" indefinitely defers the offboarding-handover problem. All three can go into a monthly inspection script that alerts on anything unexpected -- account anomalies are one of the few categories where one command line catches the problem beforehand and recovery afterwards is nearly impossible.

```bash
# /etc/sudoers.d/appops -- edit with visudo -f
appops ALL=(root) /usr/bin/systemctl restart nginx, /usr/bin/systemctl status nginx
Defaults logfile="/var/log/sudo.log"
```

## 3. Patch Management: Turning "Update" into an Institution

The firewall blocks "what has not come in yet"; patches plug "what is already public and can walk in any time" -- the gap between a CVE going public and PoCs flying everywhere keeps shrinking, which makes patch cadence the only item on the hardening checklist that races the clock. An unpatched known vulnerability is the cheapest attack entrance -- the vendor has published the fix, and the attacker only needs `searchsploit`. The core of patch management is not some command but the **cadence**: who is responsible, how often, what gets backed up before updating, and how to roll back when it breaks. Unpacked, the cadence is a set of auditable questions: when was the last full upgrade (timestamp), where is the handling SLA for high-severity CVEs written down (SLA doc), has the rollback procedure for a failed upgrade ever been rehearsed (change records) -- **failing any one of these means "we do keep updating" is a feeling, not an institution.** The update commands themselves differ little across the three families (`pacman -Syu`/`apt upgrade`/`dnf upgrade`); the differences are all in "who presses the button, how often, and who signs off afterwards" -- **at the institutional layer, the differences between the three families are always greater than at the command layer.** Making "auditable institution" more concrete: a change ticket needs at least three time fields -- **announcement date, change date, reboot-effective date** -- the gaps between them are the real exposure window, and the only convincing numbers in a postmortem.

The patch institution also has to connect with section 1's inventory and section 7's self-check: inventory decides "which packages track versions," patching decides "when to track," and Lynis/CIS decide "whether the result meets the bar after tracking." When the three are disconnected you get the classic pathology -- the software is new, the baseline is old, and Lynis reports the same few unowned suggestions every time. Reading the three sections as one pipeline makes each one's deliverable easier to remember: **the inventory, the calendar, and the remediation items**.

Patches as "vulnerability clearance" is an apt metaphor: the moment a CVE goes public, attack scripts worldwide stand at the same starting line, and your window is the gap "from advisory published to patch installed." The gap's length does not depend on whether you have automation tools but on **whether the institution specifies a deadline and an owner** -- "update as soon as possible" without an SLA stretches indefinitely into "next quarter" during a business peak. The common workable rhythm: high-severity vulnerabilities triggered by security advisories handled within 24-72 hours, ordinary updates batched through a monthly change window; with both speeds coexisting, you are neither dragged into daily reboots by the high-severity lane nor backed up into a half-yearly big bang by the ordinary one.

After tiering, define "who may press the accelerator": if everyone can take the emergency lane, the tiering does not exist; if only one person can, there must be a backup owner and a timeout escalation path. The workable form is putting the SLA into the change system -- a high-severity ticket automatically carries a 48-hour countdown and escalates when overdue -- **an institution enforced by tooling beats discipline restated in email.** Also define a minimal verification set for "emergency updates" (which services must be smoke-tested, who signs off), so that security is never used as an excuse to skip all verification and turn the patch change into a fresh source of outages.

The change window itself also needs design: a fixed weekday, avoiding business peaks, reserving rollback time, notifying downstream in advance -- teams with unpredictable windows naturally develop a "put it off" culture. Once the window calendar is set, avoid moving it; emergency patches inserted ad hoc go through the fast lane described above, and the two rhythms run in parallel without contaminating each other -- that is the structural condition for a patch institution to keep running. There is also one fixed action before and after each window: **before updating, record versions and key service states; after updating, read back the kernel/key package versions and rebuild the baselines tied to sections 5 and 7** -- without records at both ends, a successful update becomes "happened but cannot be explained" at the next troubleshooting session.

The three families' update semantics compared (mind Arch's special disciplines):

| Action | Debian/Ubuntu | Arch | RHEL/CentOS/Rocky |
|------|---------------|------|-------------------|
| Refresh indexes | `sudo apt update` | `sudo pacman -Sy` (usually folded into `-Syu`) | `sudo dnf makecache` |
| Full upgrade | `sudo apt upgrade` | `sudo pacman -Syu` | `sudo dnf upgrade` |
| Security advisory entry | ubuntu.com/security, debian.org/security | arch-security mailing list | `dnf updateinfo list security` |
| Automatic updates | `unattended-upgrades` | No official auto-upgrade (build your own timer, use with care) | `dnf-automatic` |

Two Arch disciplines deserve their own emphasis: **always upgrade the whole system with `pacman -Syu`, never a single package alone** (partial upgrades cause dependency mismatches); and **there is no "official automatic upgrade" by default** -- if you run `pacman -Syu` via a systemd timer, you must accept the operating mode of "a kernel upgrade may need manual intervention." Debian/Ubuntu's `unattended-upgrades` and RHEL's `dnf-automatic` both support installing security updates only; recommended on servers:

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # Debian/Ubuntu
# RHEL: /etc/dnf/automatic.conf -> apply_updates = yes, upgrade_type = security
sudo systemctl enable --now dnf-automatic-install.timer
```

Automatic updates do not mean "unattended and worry-free": they solve **installation** only, not **reboot-to-take-effect** and not **regression verification**. Bind automatic updates to monitoring -- alert when the kernel version changes after an upgrade, and be able to roll back services that restart abnormally -- before daring to enable it in production. Each family's automation has its boundary: `unattended-upgrades` recognizes security sources only by default, leaving ordinary feature updates to the change window; `dnf-automatic`'s `upgrade_type` works the same way; Arch has no counterpart, so if you must automate, build your own combination of timer + log collection + failure alerts, and add "upgrade failed halfway" to your drill scenarios. **Writing out automation's boundary matters more than automation itself** -- which updates happen on their own and which require human approval: operations and development need the same answer.

The actions after updating matter just as much: read the logs (`/var/log/apt/history.log`, `dnf history`, `/var/log/pacman.log`), reboot so kernel/system libraries take effect (`needs-restarting`, or check `/var/run/reboot-required`), and run the baseline self-check again (AIDE needs its baseline rebuilt; see [Intrusion Detection](./intrusion-detection.md)). **"Patched but not rebooted for three months" equals unpatched against many CVEs** -- folding the reboot into the change window is part of the hardening institution.

One often-missed question in the patch process is the division of roles: who subscribes to advisories, who executes upgrades, who verifies the business, who records the rollback point -- in a small team the four roles can be the same person, but they must **exist explicitly in the process**, or "waiting to be notified" becomes an unowned task. A workable split: security advisories arrive at a fixed mailbox/channel and get triaged, upgrades run on duty in the change window, business verification goes to the service owner, and the rollback point (snapshots, config backups, retained old kernels) is confirmed on the spot by the executor. Writing these four boxes into the change-ticket template shortens the real window more than buying another vulnerability scanner -- the scanner finds "is there a vulnerability"; the institution decides "how fast it gets patched."

Rollback itself must be rehearsed: before upgrading, confirm the snapshot can be restored, the old package versions still exist in the cache/repo, and the database has a matching backup -- **a team that has only ever rehearsed the "upgrade succeeded" path spends hours inventing a rollback plan live during its first failed upgrade.** Arch's rolling upgrades need this especially: note the key package versions before `pacman -Syu`; rolling back with the old packages in pacman's cache when necessary is steadier than looking up the wiki in a network-isolated panic.

## 4. SSH Hardening: The Highest-Priority Single Point

On most servers SSH is the **only pre-authorized public entrance**, so a configuration mistake has no "degraded but usable" middle state -- either you can still get in, or the whole machine is unreachable. Walking this section's flow until it is second nature makes later firewall and sudoers changes calmer, because your escape channel has been tested. SSH is also the only item in this page where **the config file is business continuity**: a wrong sysctl at worst leaves a parameter uneffective; a wrong sshd_config cuts the management channel on the spot -- so every discipline in this section revolves around "how to keep one mistake from becoming your last connection." Abstracted one level up, the rule generalizes to every remote-administration service (RDP, VNC, the K8s API server): **any configuration surface where a mistake severs the connection must have a verification/recovery channel that does not depend on that surface** -- SSH leans on the console, K8s on a static kubeconfig; two instances of the same principle.

SSH is the standing entrance on almost every server and the first scene of brute force. The hardening target is clear: **keys only, authorized accounts only, only the necessary authentication attempts, and the ability to get back in if the config goes wrong**. The three "onlys" address three different attack surfaces: password authentication blocks dictionary brute force, the account allowlist blocks "once credentials leak, which other identities still work," and the attempt limit blocks in-connection enumeration speed -- **the three layers are independent; cutting any one loads the other two more**, which is why baselines always carry them as a group. The three "onlys" also map to failure tests: with key login off, can password still get in (it should not); is an account outside the list rejected (it should be); does repeated failure get cut at attempt 3 (it should) -- **only a hardening you can write three tests for counts as configured.**

Putting SSH at the top of the hardening checklist rests on three reasons: it is the **only service exposed to the public internet accepting interactive logins** (business ports usually run read-only protocols or carry application-layer auth); it is a fixed target of automated scanning (password attempts against port 22 never stop); and it is the channel for all your remote repair actions -- the cost of a misconfigured SSH is not "this service broke" but "the whole machine lost management." Stacked together, these make SSH the one "mistake locks you out" high-risk change on this page and the only one worth designing a full rollback flow for. The three reasons also explain why this page covers SSH **before** the firewall: first verify the management channel works, then tighten the network surface, so the two steps' failure modes do not erupt in the same minute.

This section's configuration items are deliberately lean: only the six that directly affect exposure and authentication strength, not a few hundred directives from the man page. The common failure mode of SSH hardening is precisely "copying an over-long hardening list" -- mixed with forwarding rules that conflict with the business and timeout parameters that break CI, and after everything malfunctions the team rolls the whole thing back, taking `PasswordAuthentication no` down with it. **Every item you add must be able to name the attack it blocks and the clients it might affect**; if it cannot, do not add it. A baseline's credibility comes from "few and all correct," not "many and security-looking." A short list has one more hidden benefit: a reviewer can actually read it line by line and object -- nobody reads a thirty-line sshd_config carefully, but they will read a six-line one.

Beyond the six items there is one organizational discipline worth writing into the process: **an SSH change must run "edit config + verify in a new session + keep the old session until verification passes" in parallel**, and the verification action itself (run `whoami` in the new session, confirm authorized_keys took effect) goes on the change ticket. Many lockouts happen not because `sshd -t` was unknown, but because the operator closed the window and left right after editing, leaving the only verification chance to the next connection -- treating "new session verification" as the Definition of Done for SSH changes is the same kind of gate as running tests before a code merge.

```bash
# /etc/ssh/sshd_config (key items)
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
MaxAuthTries 3
AllowUsers ops deploy
```

The **standard flow** after editing the config (wrong order locks you out):

```bash
$ sudo sshd -t && echo $?
0
$ ssh -o PreferredAuthentications=publickey ops@server "echo ok"  # in another terminal
ok
$ sudo systemctl restart sshd    # the Debian unit name is ssh.service
```

When `sshd -t` returns non-zero, **absolutely do not restart**: the config has a syntax error, sshd will refuse to start, and once every remote session drops no one can reconnect -- ranked alongside the firewall's "enable before allow" as the two great self-lockout sources of hardening work. Key distribution and `ed25519` generation are covered in [Encryption](./encryption.md) and not repeated here.

A few more directives in `sshd_config` are worth checking against their defaults one by one; they decide not "can you log in" but "how many chances to err remain after login": `MaxAuthTries 3` pushes per-connection authentication attempts below what brute-force scripts can profit from; `AllowUsers`/`AllowGroups` draws an account-layer allowlist so that even with the password policy bypassed, accounts outside the list cannot open a session; `LoginGraceTime` shortens the handshake window so half-open connections release resources faster; `X11Forwarding no` and `AllowTcpForwarding no` (as needed) cut the tunneling capability for "log in then move laterally." All of these flip quickly, **but each should be paired with a `sshd -T | grep -i` read-back to confirm the effective value** -- written in the config file does not mean adopted at runtime; drop-in directories and Match blocks can both override lines in the main file.

Changing the port (`Port 2222`) is often cited as a "security measure," but in reality it only **reduces log noise** and cannot replace key login and Fail2Ban; if you change the port, remember to update the firewall allow at the same time (the ufw/firewalld/nft syntax for the three families is in [Firewall](./firewall.md)), or you will lock yourself outside.

One more class of "hardening that reduces availability" anti-patterns deserves naming: cranking `MaxStartups` or `ClientAliveInterval` to aggressive values, killing the multiplexed connections of normal operations or long CI sessions for no reason, so the team starts blaming the security process and eventually rolls everything back. **Every "tightening" in an SSH baseline should be paired with a "verify it still works" action** (a new session, a connection from another machine, one CI run); tightening and verification appear in pairs, and hardening stops being a tug-of-war with operational efficiency.

## 5. Kernel and Filesystem Baseline

File permissions and kernel parameters are the hardening layer with "the smallest changes, the widest coverage": a few lines of sysctl and a few checked find results defend against protocol-layer and filesystem-layer attacks that have stayed effective across a decade. This section deliberately collects only the "general baseline"; role-specific branches (containers, databases) are noted beside the parameters, to avoid pasting a gateway's config onto an application host. You can also put it this way: the earlier sections collected "what you actively turned on"; this section collects **what the kernel and filesystem hand out by default** -- plenty of exposure needs no misconfiguration from you; the factory defaults are wide enough. That also explains why this section comes after patches and SSH: **first sweep the actively opened surface clean, then come back for the defaults** -- the two passes together are what "a declared exposure surface" means.

sysctl and permission baselines share one trait worth stating up front: **they are almost never "needed" by business features, so their regression risk is minimal** -- in contrast with items like SSH or MAC where "a mistake hurts." Precisely because the risk is low, these two fit best into automated configuration management (one Ansible/Chef task each) with code guaranteeing every machine stays consistent; SSH hardening, conversely, is better walked machine by machine through the manual verification flow. **Allocating the degree of automation by change risk** is an implicit but important principle when choosing hardening tooling. Another reason low-risk items suit automation is that **their read-back is trivial**: one `sysctl` or one `find` proves effect, scriptable into a daily run; a high-risk item's "read-back" usually needs a new session and a different account, naturally resisting an unattended pipeline. The two read-back styles also imply two inspection frequencies: **low-risk items go into the daily report, high-risk items into change tickets** -- frequency is inverse to read-back cost, not proportional to risk level (high-risk items are infrequent because each verification is expensive, not because they matter less).

### 5.1 Network-Related sysctl

Kernel parameters defend against a class of **protocol-layer** legacy attacks, with small changes and steady returns. They share a philosophy with section 2's service cleanup: **turn off protocol features nobody uses, and one exploitation path disappears** -- the difference is that what is turned off here is kernel code paths, not userland processes; accordingly, the main risk of sysctl is not "the business depends on it" but "the role is wrong" (disabling forwarding on a container host, say).

```bash
# /etc/sysctl.d/99-hardening.conf (key items)
net.ipv4.ip_forward = 0
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.tcp_syncookies = 1
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.all.log_martians = 1
$ sudo sysctl --system
```

What each blocks: `ip_forward=0` turns off the default "act as a router" behavior; `accept_redirects=0` and `accept_source_route=0` plug the classic man-in-the-middle tricks of ICMP redirects/source routing (an attacker inducing you to route traffic through them); `tcp_syncookies=1` is the standard SYN flood mitigation; `rp_filter` does reverse-path validation, dropping packets whose source address could not have arrived on that interface; `log_martians` leaves a record of those suspicious packets. **Container hosts and NAT gateway machines must keep `ip_forward=1`** -- confirm the role before applying the baseline, or "hardening" cuts the business off outright. After changing, read back with `sysctl net.ipv4.ip_forward` to confirm; a correct config file does not guarantee a runtime effect. The read-back also exposes "who overrode whom": if the file says 1 but the read-back says 0, a later-loading drop-in or a runtime leftover is almost certainly to blame -- precisely the file-ordering problem covered next.

Managing parameters in separate files also deserves a note: `.conf` files under `/etc/sysctl.d/` load in alphabetical order, and a file like `99-hardening.conf`, sorted late by its prefix, can override the distro's `50-default.conf`; conversely, if your baseline file sorts before the default one, the override silently fails -- **the numeric prefix is itself part of the configuration semantics.** sysctl priority can also be disturbed by runtime changes (`sysctl -w` edits memory only); at inspection time, check both the files and the actual values read back after `sysctl --system` -- only when both layers agree has it landed. Teams can go one step further: split "role-specific exceptions" (items a container host must enable) into their own file with a scope note in the header, instead of flipping 0/1 in place inside the general baseline -- **an exception written in a comment gets copied away; an exception written in its own file can be enabled or disabled wholesale.**

### 5.2 File Permissions and the Immutable Bit

sysctl governs "how the kernel handles packets"; the permission baseline governs "**who can touch files**" -- together they form the host layer's default posture. The three checks in this subsection (shadow attributes, the SUID list, the immutable bit) each run in under two minutes and fit as fixed sections of an inspection script. Reading permission output has one trick: **hunt for "what should not be there" first, then explain "what should"** -- in the SUID list, `passwd` and `sudo` are expected; what deserves a pause is any name you do not recognize; checking top-down from the expected names burns most of your attention on familiar ones.

```bash
$ ls -l /etc/shadow /etc/passwd
-------- 1 root root 1034 ... /etc/shadow
$ sudo find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null | head
```

An unrecognized binary in the SUID list deserves digging (check capabilities too with `getcap -r / 2>/dev/null`). For extremely sensitive files, lock with `chattr +i` (even root cannot modify freely; unlock with `-i` first), suiting "never touched in normal times" files like `/etc/passwd` and `/etc/shadow` -- but **first confirm no automation writes them** (useradd and chpasswd both write shadow), or normal operations will break. The immutable bit shares its design philosophy with section 6's MAC and this section's 600 permissions: **add a counter-intuitive layer of friction to "high-value, low-change-frequency" objects**, so that both fat-fingers and low-skill intrusions stop at the last centimeter.

Three more classes of "too loose by default, must-look-during-inventory" objects belong in the permission baseline. First, **world-writable directories**: in the output of `find / -xdev -type d -perm -0002`, apart from sticky-bit directories designed that way like `/tmp`, `/var/tmp`, and `/dev/shm`, every entry should be explained one by one; a web root showing up on the list essentially means "anyone may write." Second, **over-broad group ownership of sensitive files**: `/etc/ssh/sshd_config` and application `.env`/key files should be `600` or `640` and owned by the dedicated account, and backup copies need the same tightening -- many teams harden the source file and leave `id_rsa.bak` sitting at `644`. Third, **backup and core dump paths**: if `/var/backups` or the directory a core pattern points to has uncontrolled permissions, the credentials hardening just locked down get exported sideways again. All three can be chained into one find in a weekly script whose output feeds the alert channel, complementing AIDE's change detection as "state versus change" -- AIDE catches "it changed," the weekly permission check catches "it was always loose"; **one owns the timeline, the other the cross-section.**

## 6. Default Differences Across the Three Families: SELinux, AppArmor, and "Neither"

The first five sections' configurations are broadly isomorphic across the three families (different package names and paths, same concepts); MAC is one of the few whose **default shape is completely different**: one side ships Enforcing out of the box, one side has AppArmor standing guard, and one side has neither. Memorizing "the defaults differ" as a table is more reliable than guessing commands on each machine. This section also reads differently from the earlier ones: those pursued "the same outcome on all three families"; this one first admits **the outcomes genuinely differ**, and the goal downgrades from "unified configuration" to "unified understanding of each default, then decide whether to align" -- when checklists get copied across distros, MAC is almost always the line that breaks. If you maintain a single distro only, this section is still worth reading: **knowing what the neighboring distro enables by default is how you know whether your "no denials reported" means a tight policy or nothing intercepting at all.** The check itself deserves a fixed one-liner: `getenforce || aa-status || echo "no MAC"` -- pasting that three-way output into the change ticket reconciles far better than saying "MAC is on" verbally.

Mandatory access control (MAC) is a second gate above DAC (rwx): even if a process is compromised and gains high privilege, policy it does not allow keeps it away from sensitive objects. **The three families differ completely by default, and so do the triage entry points** -- the place where cross-distro operators most easily "run the wrong command and blame themselves." This section does not expand into policy authoring (that lives in [Basics · Security Basics](../basic/security.md)); it solves the three most practical questions of the hardening scenario: does this machine have MAC, where to look when something is denied, and when to allow rather than disable. All three are answerable within one minute of logging in -- which is why MAC belongs on the go-live checklist rather than "research when there's time." The one-minute check itself has two failure shapes to distinguish: **the command does not exist** (not installed/enabled; see the table) versus **the command exists but denials are zero** (maybe no denial has ever occurred, or the policy is too permissive) -- the latter needs one more small experiment known to trigger a denial to confirm the policy actually intercepts.

To understand why MAC deserves its own section, first accept an uncomfortable fact: DAC (rwx/ownership) assumes "whoever holds high privilege may do anything," while in reality most intrusions are precisely **gain high privilege first, then act** (a web process hit by RCE, sudo configuration abused). MAC breaks exactly that assumption -- it asks not "do you have root" but "**is this process permitted to touch this file**." An nginx worker, even compromised into root, cannot touch `/etc/shadow` under SELinux Enforcing, because its type label simply lacks that permission. It is a third independent line of defense beyond the firewall and least privilege, and the only control in this page's checklist that defends "after compromise" rather than "against compromise."

Treating MAC denial logs as an "allow wizard" rather than an "error message" is the operating attitude this section most wants to convey: every denial is a precise permission request slip -- it tells you which domain, which type, which operation was blocked. Read them one by one, allow one by one, and the policy grows into a shape that fits the workload as the business runs; conversely, silencing the log level or switching wholesale to Permissive throws the slips away, and months later the first Enforcing run drowns you in hundreds of historical denials with no idea where to start. **A security policy's maintainability comes from "allowing in small steps," not from "getting it right in one shot."**

| Comparison | Debian/Ubuntu | Arch | RHEL/CentOS/Rocky |
|--------|---------------|------|-------------------|
| Default MAC | AppArmor (enabled) | Neither SELinux nor AppArmor enabled by default | SELinux (Enforcing) |
| Check status | `aa-status` | If you enabled SELinux yourself: `getenforce` | `getenforce` / `sestatus` |
| Denial logs | `/var/log/kern.log`, apparmor entries in the journal | Depends on which scheme you enabled | `/var/log/audit/audit.log`, read with `ausearch` |
| Main triage commands | `aa-status`, `dmesg \| grep apparmor` | -- | `ausearch -m avc`, `sealert` |

Running `getenforce` on Ubuntu and getting empty output or `command not found` is **not you doing it wrong -- this machine simply does not use SELinux**. The shared advice across the three families at this layer: **do not turn MAC off because it gets in the way** -- disabling SELinux on the RHEL family forfeits the type-label assumptions of a large set of services along with it; turning AppArmor off on Ubuntu dismantles the second gate. The correct posture is to read the denial logs and make minimal allows; the concepts and command details are in [Basics · Security Basics](../basic/security.md), the SELinux diagnostic loop is in [SELinux in Practice](../security/selinux.md), and AppArmor profile writing and the `aa-logprof` fix trajectory are in [AppArmor in Practice](../security/apparmor.md); this page only nails "the three families' defaults differ" into the baseline checklist.

"Minimal allow" operationally means one fixed path: reproduce the denial -> copy the complete avc/denial from the log -> generate candidate rules with `audit2allow` (SELinux) or `aa-genprof` (AppArmor) -> **manually delete the over-broad parts unrelated to this case** -> apply and retest. The final "manual trimming" step cannot be skipped: adopting tool output directly commonly grants a process an entire class of permission, degrading the defense from "as needed" to "as the tool defaults." Allow rules belong in a config repo like firewall rules -- diffable and rollback-able -- because MAC policy, like iptables, is living configuration that colleagues and automation will keep rewriting.

The Arch reality: **DAC + firewall + least privilege is the factory baseline**; wanting MAC is advanced customization with no "copy the RHEL docs" shortcut. Knowing that premise, you can understand why many RHEL-oriented hardening checklists come up "half missing" on Arch.

Beyond the three families there is one more practical constraint: **containers and orchestrators are taking over part of MAC's job** (seccomp, AppArmor profiles, Kubernetes SecurityContext), so a distro that does not enable host SELinux is not necessarily "entirely without MAC" in container scenarios. But that is not a general reason to skip host MAC -- when the host line falls, post-escape lateral movement inside containers still leans on host-layer policy to catch it. Evaluate by deployment form: bare metal/VMs go by this section's three-family table, containers go by the platform's security context, and only the two stacked give the full picture.

## 7. Baseline Self-Checks and Compliance Tools

Every item in the first six sections can be executed by hand; the problem is that **people get tired, miss things, and copy last round's results on the third inspection**. A tool's real value is not "discovering new problems" but **repeatedly exposing regression under the same standard** -- exactly the dividing line between an "institution" and a "campaign-style check." You can also say: the manual checklist guarantees depth (understanding this machine's business), tool scanning guarantees breadth and cadence (the same day, the same version, the same expectations, run again); miss either and you degrade respectively into "an experience-driven lone hero" or "an unowned scan report." This section's landing point is therefore not "which scanner to pick" but **how to make one scan's output become the next scan's baseline** -- a scan that deposits nothing is just anxiety in a different format. Depositing scan output can be plain: export each round's suggestion list as CSV with a date into the repo, and diff by number three months later -- **security output that can be diffed drives remediation; output that cannot is just screenshots.**

Manual checklists executed item by item are the most reliable but depend on the executor remembering everything; tool scans win on coverage and repeatability, and lose on not understanding your business context. The relationship is not either/or but **the tool sets the questions, the human grades the paper** -- this section makes that collaboration explicit and gives a starting tool common to the three families. It also deliberately introduces exactly one starting tool: Lynis covers "blind-spot discovery for general hardening" well enough; stacking CIS/STIG/homegrown scripts on top only manufactures three sets of mutually contradictory "authoritative scores" -- **a self-check system's credibility comes from long-term comparability, not from the item count of a single scan.** A single tool has one more organizational benefit: the team only has to agree on one vocabulary (hardening index, suggestion numbers) to run a remediation meeting; with multiple tools coexisting, even the definition of "high risk" takes half an hour to align first. The third selection criterion for a starting tool is **the same name on all three families**: Lynis installs from `apt`/`pacman`/`dnf` alike with consistent output structure, so cross-distro comparisons avoid tool variance as a confounder.

A manual checklist inevitably misses things; running a tool over it fills the blind spots. Self-check tools complement the manual processes of the earlier sections rather than replacing them: the manual checklist guarantees "every business-relevant item on this machine passed," the tool guarantees "the general items you never thought of got scanned too." Lynis is an open-source security auditing tool common to all three families; it outputs suggestions organized by a "hardening index" and makes a good starting point for baseline self-checks:

```bash
sudo apt install lynis                # Debian/Ubuntu
sudo pacman -S lynis                  # Arch
sudo dnf install epel-release && sudo dnf install lynis   # RHEL family
$ sudo lynis audit system --quiet
```

Lynis's `suggestions` will include plenty irrelevant to your business -- **do not adopt them wholesale**: treat it as a "check-item generator," judge each one against this machine's threat model, fold the applicable ones into the baseline document, and record the rest as "evaluated, not applicable, and why." CIS Benchmarks are the standardized version of the same idea (stricter items per distro/role), suited to environments with compliance requirements; individuals and small teams can start with Lynis plus this page's checklist without chasing full CIS compliance from day one -- **a maintainable 80% baseline beats an unexecutable 100% checklist.**

The "disposition loop" for tool results matters more than the score itself: Lynis's hardening index is good for trends (did this round beat last round) and bad for comparing absolute values across machines -- machines of different roles were never comparable to begin with. The correct use is to walk every suggestion through a three-state flow of "adopt / evaluated-not-applicable / deferred with reason," with the output being a remediation list that carries status, not a screenshot of a score. When compliance demands arrive, bring in CIS automated auditing (`ansible-lockdown`, the distro's STIG toolchain) and use this page's checklist as the guided tour for "understanding why each item exists" -- the tool tells you which rule you fail; this page helps you judge whether that rule is worth the performance and operational cost under your threat model.

## 8. Common Pitfalls

The ten below unfold in the order "locks you out / breaks the baseline / idles the institution" -- the first few can leave you unable to reach the machine on the spot, the middle ones make the config look right while being ineffective, and the last few let the whole hardening effort slowly fail over months. Each maps back to one section's discipline; jump back to that section when an unfamiliar number appears -- **the pitfall list is not an appendix, it is the body's reverse index.** Slicing the ten by "when it surfaces" also helps: lockout types show up during the change itself, ineffective types surface at the next read-back or scan, and idle types only at the quarterly review -- **the later the category, the more its check must live in a fixed rhythm rather than on-the-spot intuition.** The three types also differ in root cause: lockout stems from **missing verification steps**, ineffective from **missing read-backs**, idle from **missing owners** -- correspondingly adding "new-session verification, effective-value read-back, remediation-item assignment" covers essentially the prevention surface of all ten. Writing those three actions straight into the change-ticket template beats posting another "security notices" page on the wiki -- **templates enforce; notices only raise probabilities.**

1. **Restarting after editing `sshd_config` without `sshd -t`.** A syntax error keeps sshd from starting; every session drops and no one can reconnect. The flow is always: syntax check -> keep the old session -> verify in a new session -> only then restart.
2. **Turning off `PasswordAuthentication` before distributing public keys.** The reversed order locks you out instantly. Verify key login successfully first, then turn off passwords; keep the cloud console as an escape hatch.
3. **Editing `/etc/sudoers` by hand outside `visudo`.** One typo takes sudo down for everyone, including the tool you would use to fix it. Always `visudo -f /etc/sudoers.d/file`.
4. **Piping `pacman -Qdtq | pacman -Rns -` without reading the list first.** You may delete manually installed tools that merely have no dependents right now (a monitoring agent, say). Run `pacman -Qdtq` alone, review it, then pipe.
5. **Applying `ip_forward=0` to a container/routing host.** Docker and KVM NAT hosts must forward; a blanket disable breaks the business. Baselines must branch by role.
6. **Not rebooting and not rebuilding the AIDE baseline after updating.** Kernel and glibc updates do not take effect without a reboot; an AIDE baseline left stale turns the next scan into pure noise. Both belong on the change-closing checklist.
7. **Mixing MAC concepts across the three families.** Checking SELinux on Ubuntu or AppArmor on RHEL both find nothing. Pick the tool from the [three-family comparison table](#_6-default-differences-across-the-three-families-selinux-apparmor-and-neither) first.
8. **Locking files with `chattr +i` that automation writes.** useradd/chpasswd need to write `/etc/shadow`; locked, all account operations fail. Confirm the writers before locking.
9. **Executing every Lynis suggestion wholesale.** Role-blind "adopt everything" manufactures piles of ineffective config and performance overhead. Evaluate item by item and record the trade-offs; that is baseline management.
10. **Never revisiting after hardening.** Ports, accounts, and services bloat again as the business changes. Turn the inventory commands of sections 1, 2, and 4 into a monthly inspection script, and hardening becomes an "institution" rather than a "one-time campaign."

Grouping by nature helps systematic self-checks: items 1-3 are **single-point mistakes that lock yourself out** (process discipline problems, cured by a fixed order of operations); items 4-6 are **baselines applied to the wrong role or a broken update chain** (branch by machine role; write the closing actions into change tickets); items 7-9 are **wrong ways of using tools** (the three families' concepts, chattr, and lynis are all "knowing the commands is not using them correctly"); item 10 is the **missing institution** -- the first nine guard against a particular incident while it guards against "everything slowly going bad." The inspection script need not be fancy: save the outputs of `ss -tulnp`, `systemctl`, the package list, and the key `sshd -T` items as dated snapshots, diff against the previous run, and the anomalies surface on their own.

## 9. In Practice: The Hardening Checklist for a New Server Going Live

The first eight sections unfold by topic; the practice section strings them by **chronological order** into one executable go-live flow -- the only place in this page where "you must follow the numbers" applies, because real dependencies run between the nine steps, not typographic preference. If only one page of this page could be kept, it is this section: the first eight own the "why," this section owns "in what order to act and how to accept each step." Those who print the nine steps and pin them at their desk will find only two spots need real thinking -- the judgment of step 1 (what counts as redundant) and the synthesis of step 9 (how to fill the five columns); the other seven are **mechanical actions with one correct order** -- mechanics go to the checklist, judgment stays with the human; that is the shared structure of every security runbook. The nine steps also deliberately do not demand "all at once": **the first pass may finish only 60% with the remainder recorded as remediation tickets** -- more valuable than chasing a perfect score but stalling three days on step 1's inventory. Baselines are iterated into existence, not憋出来的. Under the iteration view, "done" also loosens: not "all green" but "**no item is unowned**" -- what was done has a record, what was not has a ticket; that resists the next drift better than a sprint to all green.

Execute in order, with every step independently verifiable (install across the three families with `apt`/`pacman`/`dnf` respectively; the Arch examples below use `pacman`). The nine steps are not nine options but one dependency chain: **inventory produces scope -> patching fixes the baseline version -> SSH narrows the entrance -> the firewall narrows the network surface -> detection installs eyes -> kernel and permissions pull in root privileges -> MAC/self-check do verification -> archiving leaves evidence.** The common consequence of skipping steps is "the later steps stand on assumptions the earlier ones never defined" -- installing AIDE before inventorying, for instance, bakes a pile of temporary packages into the baseline that must be cleaned afterwards. The chain also has a reverse acceptance order: **acceptance should walk backwards from the five-column document of step 9** -- every column pointing back to some step's read-back output means the chain is complete; a blank column means not that column is missing but that its step was never done or left no trace. Walking backwards has one psychological bonus: **starting from the deliverable and asking "where is the evidence" is harder to self-deceive than starting from the steps and asking "am I done"** -- the former requires pasted output, the latter only a nod.

Three preparation actions deserve a place at the head of the runbook before the checklist runs. First, **confirm the console/rescue channel works** (test VNC once on a cloud host, confirm IPMI/iLO on physical hardware) -- the precondition for daring to do steps 3 and 4. Second, **prepare a "mid-change" time box**: the nine steps take hours end to end, and getting interrupted at the SSH step is the most dangerous, so leave an uninterrupted window around step 3. Third, **open a change ticket**, ticking off each step and pasting the read-back output -- half the checklist's value is in execution, half in the trail it leaves; hardening without a trail has to be redone wholesale at the next handover. The three share one failure-mode assumption: **default to "the executor will be interrupted mid-way, will misremember, and will close the window"** -- a runbook's redundancy exists not for veterans but for the newcomer running it for the first time three months later. The quality of handover between old and new executors ultimately lands on the change ticket: **a checklist the next person can pick up and continue is the only one that truly finished.**

Besides the patch->baseline->self-check thread mentioned earlier, one more hidden line -- the **evidence line** -- must run through all nine: the step 1 inventories are evidence, the step 3 and 4 read-back outputs are evidence, the step 7 and 8 scan reports are evidence, and step 9 nails them into the same document. A security audit never asks "have you done hardening"; it asks "**show me the record of the last hardening**" -- treat the evidence line as part of the deliverable, and the finished checklist automatically satisfies the shared format of internal and external audits, with no after-the-fact paperwork.

The checklist also implies a **rollback budget**: the genuinely high-risk steps are 3 (SSH) and 4 (firewall), which share one failure mode -- the remote channel dies while the console is not ready. The time box and the rescue channel are not ceremony but insurance bought for those two steps; steps 1, 2, and 5-8, even done wrong, can essentially be fixed over a local or out-of-band channel. Color the nine steps by "rollback difficulty" (red/yellow/green) when printing -- more usable than a linear list -- **a change ticket's priority should be set by rollback cost, not by step number.**

1. **Inventory**: `ss -tulnp` for listeners, `systemctl list-units --type=service --state=running` for services, `pacman -Q --explicit` (or `apt-mark showmanual`/`dnf repoquery --userinstalled`) for packages; remove/disable what is unrelated to the business. The deliverable is three lists, pasted straight into the step 9 archive document.
2. **Patches**: full-upgrade to the current version (`sudo pacman -Syu` on Arch), confirm reboot needs, and schedule the reboot window. Patching sits after inventory and before SSH because SSH hardening is best built on "the current version of sshd" -- discovering an authentication bug in the old version after passwords are already off makes the flow awkward; level the version baseline first so later configuration changes stand on stable ground.
3. **SSH**: distribute ed25519 keys -> `sshd -t` -> verify in a new session -> edit `sshd_config` (disable root, disable passwords) -> restart -> **keep the old session and verify once more**.
4. **Firewall**: default-deny inbound, allow SSH first then enable (order in [Firewall](./firewall.md)), and sync the cloud security groups. The firewall comes after SSH rather than before it so that, once SSH hardening is done, tightening the network surface can immediately be verified with the "keys + new policy" combination -- in the reverse order you would run naked for a stretch through the window where passwords are already off but the firewall is not ready.
5. **Detection**: install AIDE + Fail2Ban + auditd, initialize baselines, and wire alerts (see [Intrusion Detection](./intrusion-detection.md)). Detection initializes its baseline after the configuration has largely settled, which sharply cuts the reruns of "baseline no sooner built than washed away by the next change"; reversed (init first, then the heavy configuration of steps 3 and 4), the baseline is stale by the time step 5 finishes -- done for nothing.
6. **Kernel and permissions**: write the `sysctl.d` baseline and read back with `sysctl --system`; spot-check the SUID list; tighten the sudo allowlist.
7. **Confirm MAC status**: check with `getenforce`/`aa-status` per the distro, and record the current state and whether it matches expectations.
8. **Baseline self-check**: run `lynis audit system` over the suggestions; fold the applicable ones into the checklist and record reasons for the non-applicable ones.
9. **Archive**: write "what ports this machine opens, what services it runs, who has sudo, key fingerprints" into a one-page document in the repo -- **hardening without documentation leaves nobody able to say, three months later, which parts were intentional.**

With the nine steps done, the machine's attack surface has converged from "the default-install full set" to "the business-declared subset," with every configuration traceable. Note that steps 2, 5, and 8 form a dark thread that is easy to omit: **patching changed files -> the detection baseline must be rebuilt -> the self-check results refresh accordingly** -- hardening without detection means configuration drifts unnoticed; detection without hardening means every scan re-alerts on the same known issues. The checklist's completeness matters more than any single step's polish. The thread extends one link further: remediation items from the self-check must flow back into step 1's inventory and section 3's change windows, or they become the standing noise of "Lynis reports the same few every time" -- **the nine steps are actually a loop: step 8's output feeds the next round's step 1; it is not an endpoint.**

The checklist should also come with an "escape card" pinned to the first page of the change ticket: how to reach the cloud console VNC when SSH fails, how to fix a broken sudoers from a live ISO, which cache/repo to reinstall an accidentally deleted package from. If any of the nine steps locks you out, what decides recovery time is not how well you know the config but **whether the escape channel was verified in advance** -- an untested VNC is very often grey exactly on the day you need it. Make "verify the escape channel works" step 0 of the process; it costs five minutes and buys the courage to act through the other eight. The escape card should also carry one line of **local information**: which account the machine lives under, what the IAM role is called, which queue the ticket goes to -- without those, even a bright VNC is an entrance the newcomer cannot find.

The archived one-page document should have five fixed columns: listening ports and source restrictions; running services and the reasons they are on; the sudo/privileged account roster; key effective SSH and firewall values (`sshd -T`, a `ufw status` summary); key and certificate fingerprints/expiry dates. The five columns correspond to the outputs of sections 1, 2, 4, and 5, diffed column by column at monthly inspection -- **the document is not decoration written for the auditor; it is the comparison baseline for your or a colleague's next change.**

The essence of hardening is this sentence: **bring the system back to a state you actively chose, and keep it there.** "Actively chose" is the shared subject of all nine steps -- choosing means explainable, read-back-able, rollback-able; "keep it there" means the periodic self-checks of sections 7 and 8 are not an appendix but the second half of that sentence itself. If only one line can be left for the team to pin on the wall, take the second half: **most people do not lack the awareness to harden once; what they lack is still remembering to come back and reconcile in the third month.**

## References

Hardening material is abundant and wildly uneven in quality; here it is tiered by use: **CIS Benchmarks** are the authoritative checklist when compliance demands (split by distro and server role; long but trimmable); **the Arch Wiki and each distro's official security docs** are the primary source for understanding "why this family's defaults are what they are"; **Bird's Private Recipes and mature blogs** build intuition well, but specific parameters must be verified against the current distro manual -- hardening items iterate fast, and a three-year-old "best practice" may already be void or reversed in a new release. Use this page's checklist as the skeleton, cross-check blind spots with CIS, and verify each item's three-family differences against the official distro docs. The three tiers also expire at different speeds: CIS is revised with major versions, distro docs track the package manager and service names, and a blog may be stale by the next Ubuntu LTS -- **when verifying, the copy nearest your machine wins** (local `man`, your own distro's docs); external material's job is only to raise the questions.

A practical reading-order suggestion: first walk the CIS chapters corresponding to this page's section 9 steps in order, writing "we do not adopt this, and why" into the notes; then verify the three-family differences in the tables against the official distro docs; only then use Lynis as the periodic scanning backstop. Reading the CIS full text first is the easiest way to die in the first 50 business-irrelevant details -- no framework built, no executable checklist formed -- **checklist documents are read by subtracting from scenarios, not by fill-in-the-blank from top to bottom.** The value of the "not adopted, and why" column rises with time: two years later, when someone asks "why did we not enable this," you can point at the note and say "evaluated, because the containers run ..." instead of opening a fresh security review -- **the record of subtraction matters as much as the configuration of addition.**

The three checklists (section 9 of this page, section 8 of the firewall page, section 8 of the intrusion detection page) belong together in a `security/baseline/` directory of the same config repo, version-controlled alongside the sysctl fragments, sshd_config, and nftables.conf. That way every repo diff changes not just configuration but also "the security posture we claim" -- **the code review process incidentally becomes the security review**, the lowest-cost path for wedging the hardening institution into existing engineering habits. The repo can hold one more layer: the "escape card" and the archive template (step 9's five-column table), so a new machine goes live by copying the template and editing the differences rather than starting from a blank document: **templating is the dividing line between an institution that "lives on the wiki" and one that "runs in git."** The repo-to-checklist relationship compresses to one line: **the checklist is the interface, the repo is the implementation** -- with the interface stable (five columns, nine steps unchanged), the implementation can evolve with the toolchain; even if Lynis gets replaced next year, the framework you learned from this page still holds.
